# 真实历史事件准入

SWE-bench Verified 提供真实 issue、`base_commit`、修复 patch 和测试。它不自动提供执行中途的有效变更。时间上更晚的 `change_commit` 只是搜索条件。

15 到 20 条候选是搜索量。正式样本要六项全部通过。凑不满五个完整事件对时，停止 benchmark 扩展，不改写历史，也不编造 issue。

## 六项

| 项 | 通过 | 拒收 |
| --- | --- | --- |
| 时间有效 | issue、PR、base、change 的时间和祖先关系都有记录，change 是 base 的后代 | 时间倒序，或无法证明祖先关系 |
| 来源真实 | commit 或 PR 的 URL 和完整 SHA | 只有短 SHA，或来源是人工改写 |
| 可应用 | 在规定基线上重放成功 | 冲突。失败仍要留下分类，不能从记录里删掉 |
| 任务未被直接解决 | 更新不包含、也不泄漏原任务的目标修复 | 后续提交已经修好了原问题 |
| 变更后可解决 | 有 Agent 可用工具下的参考恢复路径，或可核验的修复见证 | 无法证明新状态还能完成任务 |
| 独立评分 | 变更后的要求能由测试或明确规则检验 | 只能靠阅读模型自述 |

另三个字段分开标，定义在 [annotation_guidelines.md](annotation_guidelines.md)。文件路径有交集不是相关性的 gold label。

无法证明变更后仍可解决时，Agent 的失败不能写成恢复能力不足。

## 变更后的四套评价

- 原始任务测试：Clean 上是否具备基础修复能力。
- 变更后状态测试：更新后的要求是否满足。原始 FAIL_TO_PASS 在 API 或预期变了之后可能不够，也可能和新要求矛盾。
- 证据规则：是否使用了已失效证据，该刷新时有没有刷新。
- 工作保留：原先必须继续成立的功能和副作用是否还成立。适应新 API 而改写代码，可以是正确的。不按原始 diff 行数计分。

`reference_recovery_witness` 只给数据集验证和评分审计。它不进入 Agent 工具、挂载、环境变量或检索索引。

## 切分

同一基础任务的 Clean 和全部变更变体留在同一个集合。同一 commit 或其直接衍生变更不跨开发集和留出集。同一模板的改写尽量不跨集合。另设 repository-held-out。数据支撑不了仓库留出时，不写跨仓库泛化。

主统计单位是基础任务根。同一仓库有多条任务时，另报仓库聚类。
