# 可靠性发现与投稿判断

这篇文章只使用已经落盘的测量：旧 360 格、新 120 格重复、E1–E3、E5–E8、容器与宿主对照，以及离线协议测试。冻结稿 `docs/现行/论文/` 没有改。旧 360 和新 120 的故障构成不同，下面不把它们加成一个总成功率。

## 现在能不能投三四区

可以作为一篇测量型文章的骨架，投中科院三区偏紧，四区在把适用范围写清楚之后更现实。这不是录取判断。能送审的贡献是：同一套受控任务里，任务终态、过期写入、合法后继、回执和物理字节是不同的量；一种保护只改善其中一列。不能送审的写法是“Full 把 Agent 成功率提高了 25 个百分点”，也不能写成“有 fencing token 就能挡住任何过时工具效果”。

投稿前正文必须改三处，否则审稿人用原始格子就能驳回：

1. 新批次里 Commit-only 的库存过期写入发生时，Run token 仍是 1。`supersede` 只注入了 Full。这 10 次证明的是资格检查看不到带外的库存文件变化，不是它接受了已经被替换的旧 token。
2. 每臂 10/40 与 20/40 的 Wilson 95% 区间是 0.1419–0.4019 和 0.3520–0.6480，两者重叠。25 个百分点是点估计，识别对比在 `state_change` 这一组，不在四组加总。
3. 旧 E4 的 `version_mismatch` 让文件后继完成了 10/10。那条路径核对的是 Run token，不是 EffectSink 版本。它不能用来证明“sink 没对齐时后继会被拒绝”。后一条只在 `commit_authorized` 的离线测试和 E2 里。

## 五条发现

Agent Runtime 的可靠性由状态通知、执行资格、效果提交、物理效果、恢复证据和合法进展共同决定。一种执行保护可以改善其中一个性质，不自动保证其余性质。F1、F2、F4 适合做主体。F3 是适用边界。F5 是这台机器上的成本，不是集群结论。

### F1 拒绝旧动作，不等于合法后继完成

旧 360 格里，Direct 和 Full 的任务终态都是 60/120。Wilson 95% 区间都是 0.4119–0.5881。Full 的无过期写入是 110/120（区间 0.8534–0.9541），Direct 是 60/120。Full 有 50 次合法后继，Direct 的受控后继是 0。

这 60 格成功并不是同一批格子。12 个故障组各 10 格：

| 组成 | 格数 | 故障组 |
| --- | ---: | --- |
| 两臂都成功 | 20 | `approval/retry`，`coding/stale_credential` |
| 只有 Direct 成功 | 40 | 三组 `receipt_loss`，`coding/publish_failure` |
| 只有 Full 成功 | 40 | `inventory/state_change`，两组 `version_mismatch`，`coding/concurrent_edit` |
| 两臂都失败 | 20 | `inventory/missing_notice`，`approval/permission_revoked` |

Full 的 50 次后继里，40 次落在“只有 Full 成功”的格子上，另外 10 次是 `coding/stale_credential`：规格文件没有改，Direct 写成 `return 1` 也算终态正确。安全拒绝和任务终态因此可以反向移动。`approval/permission_revoked` 的 Full 是 0 次过期写入、0 次任务成功：停下来没有把审批写成当时的 `DENY`。

新 120 格把同一件事再拆开。每臂 40 条，任务终态是 Direct 10/40、Commit-only 10/40、Full 20/40。多出来的 10 次全部是 `inventory/state_change` 的合法后继。永久撤销的 Commit-only 和 Full 都没有文件，任务终态仍是 0。Claim 后、替换前恢复的 Full 终态是 10/10，合法后继是 0，因为完成的是同一次已授权发布。

### F2 资格检查、fencing 和效果恢复不能互相替代

三臂测的是三件不同的事。Direct 不查资格。Commit-only 在发布门之后做一次 `admit()`，`admit()` 与 `writeFileSync` 之间没有第二次校验。Full 走 claim、暂存摘要和发布。`supersede` 只推进 token 和版本，Run 仍可以 `eligible`，所以一次资格检查本身不是 fencing。

新批次里，永久撤销对三臂都在开门时注入。Direct 10/10 写下 `permit ALLOW`。Commit-only 和 Full 10/10 没有目标文件。这说明门后的一次资格检查能够挡住已经写入控制面的撤销。

库存 `state_change` 不能写成“Commit-only 在 fencing 下仍写旧值”。这一组对所有臂都把 `stock.txt` 从 3 改成 0，但只有 Full 调用 `supersede`。Commit-only 的样例格 `final_token` 仍是 1，`eligible` 仍是真，文件是 `order 3`。它和 `missing_notice` 同属带外状态变化。真正表明“资格检查不是 fencing”的记录是单元测试：`supersede` 不取消资格；`admit()` 已经返回允许之后再发生 `revoke`，写入仍然发生。

恢复也不替代前两件。`recover_claimed_publish` 只接受同一本 RunLedger 上对得上的 `run_id` 和幂等键。Claim 提交之后的撤销仍可完成这一次已授权发布。Claim 之前没有可恢复的行。已完成摘要冲突不改回执。暂存丢失是 `unknown`，不合成完成。目标内容不同是 `conflict`，不覆盖。外部写入者不走账本锁，`os.replace` 会把它覆盖掉。

### F3 没有可信通知时，Full 仍会发布过时效果

旧 360 的 `inventory/missing_notice` 上，Full 是 10/10 写成 `order 3`，库存已经是 0，没有 `supersede`。新 120 格同一组仍是三臂各 10/10 过期写入。

受测保证是：相关状态变化已经进入控制面的资格状态之后，过期凭证可以被拒绝，合法后继可以完成。它不包括“持有 fencing token 就能挡住任何基于过时世界状态的工具效果”。这条放在发现和效度威胁里，不放在末节一带而过。

旧稿已经把“没有通知则旧 token 仍写入”写成观察。E4 给它加上了任务级计数，并说明 Full 臂在这条故障上和另外两臂一样。

### F4 回执状态不是物理效果状态

效果证据要绑定实际发布的字节，而不是只绑定先前验证过的路径。内容摘要和 TOCTOU 都不是新机制。这里的材料是一个工具执行故障模型、一个旧实现反例、两种 Publisher，以及把物理效果和回执分开的评分。

第一类是回执丢失、效果已经接纳。E5 在本地接收端上：同键同载荷是 `replayed`，接受次数 1；同键不同载荷是 `conflict`，原载荷保留。接纳之后、回执之前 `SystemExit(86)`，对账是 `confirmed_from_sink`，接受次数仍是 1。E6 用 `TerminateProcess` 杀掉已经接纳、账本还没有效果行的进程，重开后同样对上，接受次数仍是 1。未提交事务里把 token 改成 99 再杀进程，重开后 token 仍是 1。这不是断电，也不是任意 HTTP 服务的 exactly-once。

第二类是已经读过的暂存，在物理发布时内容变了。原始字节的 SHA-256 是 `050d3aac3ac80d43bcadb8c6c34420ad6cef6d61a59b06141604e7c085e165fb`。容器 Publisher 在替换和截断之后仍写出这份已读字节，回执核对通过。宿主 `publish_file` 按路径 `os.replace`，两次都是 `unknown`、无回执，落盘摘要等于改过的字节。读文件过程中被截断的内核窗口没有测，两边都标了 `kernel_toctou: false`。

旧 360 的 `receipt_loss` 是 Claim 成功、替换还没发生就返回。Full 的 30 格对账都是 `unknown`。库存和审批的目标文件不存在。编码的 `bug.py` 仍是开始时的 `return 0`。原评分器在文件还在时把这组的 `unknown_fraction` 记成 0。新的 `outcome_known` 仍是假。标签保持 `receipt_loss`，机制注明是 `claimed_before_replace`。新 120 格的 Full 在同一崩溃点调用恢复，10/10 完成已授权发布。

`retry` 给出效果身份的另一列。Direct 和 Commit-only 在 10 次里多出 30 次 `eg_write`。Full 只有一条 completed 效果，第二次是同一键的重放，重复写入计 0。

### F5 正确性检查有局部成本，端到端墙钟仍由模型决定

三套开销回答不同的问题，不能相减。

| 实验 | 能说明的事 | 不能说明的事 |
| --- | --- | --- |
| E7 内存库，单连接，每种操作 60 次 | 本地控制操作的耗时 | 持久化吞吐 |
| 旧 E7 文件库，同一进程里每线程一条连接，每档 3 批 | 这台机器上线程争用的一次样本 | 独立试验，也不是多机 |
| 新 E7，每批一个新库、一个新进程，预热丢掉，正式 30 批 | 批次中位数和这批的吞吐 | 480 次操作不是互相独立的确认实验 |
| E8 在线 `deepseek-flash`，每臂 20 次 | 单次短调用里模型占墙钟 | 论文里那组 0.878 / 1.034 / 1.067 秒 |

内存库单次 supersede 的 p50 是 0.084 毫秒。旧文件库并发 1 的 p50 已经约 8.237 毫秒。这两列不能相减当成锁等待。

新 E7 读到 `journal_mode=delete`，`synchronous=2`。延迟从连接打开之后的 `supersede` 算起。并发 1 的批次中位数 p50 是 0.045877 秒，操作 p50 同值，吞吐 p50 是 21.2266 次/秒。并发 16 的批次中位数 p50 是 0.381143 秒，操作 p50 是 0.370217 秒，操作 p99 是 0.796388 秒（480 个操作样本），吞吐 p50 是 23.188823 次/秒。吞吐中位数上升 9.2%。在这套单机 DELETE journal、同步落盘的配置下，受测版本更新路径的吞吐扩展有限，增加并发主要增加了操作延迟。这不能归因到某一种锁，也不能写成 EpochGate 在高并发下不适用。

E8 新的在线调用里，B0、B1、B2 的模型 p50 是 0.724、0.735、0.823 秒，控制面 p50 是 0.000002、0.000246、0.000202 秒。离线固定轨迹的控制面 p50 是 0.000176 秒，恢复 p50 是 0.000028 秒，模型时间是 0，因为没有调用模型。论文冻结稿里的三臂总时间是另一次实验，保留原数，不与这次混写。

## 评分本身会掩盖一列

Direct 和 Commit-only 在旧 360 格的 `outcome_known` 是 0。它们的写入不经过效果回执。文件存在不能单独把结果判成已知。这是指标定义，不是这两臂把文件弄丢了。

Full 的 `outcome_known` 是 90/120。30 个未知都是旧 `receipt_loss`。正确停止只有 10 格，全部是审批被永久撤销的 Full：资格已撤销、目标文件不存在、没有过期写入，任务完成仍是 0。`coding/publish_failure` 的 Full 不是正确停止。`bug.py` 在任务开始前就存在，撤销后文件还在；该格有 `result_withheld`，所以结果已知为真、正确停止为假。

旧 token 合计不能用于 API 成本。360 格的 input 是 419107，output 是 181006，二者之和 600113，格子里的 total 加总是 9690545。原始帧没有保存。计数已经改成每个顶层帧只取第一份 usage，新格子的 total 等于 input 加 output。

## 两批 E4 为什么可以同时成立

旧批次是 3 类任务、12 个故障组、每组 10 次、三臂，共 360 格。`permission_revoked` 的撤销只注入 Full，所以旧的 Commit-only 在这一组和 Direct 一样写下了过期审批。文件路径上的 `version_mismatch` 只推进 Run token。编码终态用进程里的语法树读取 `value()`，不是容器评分。

新批次是 4 个故障组、每组 10 次、三臂，共 120 格。永久撤销改为三臂都注入。`claimed_before_replace` 的 Full 在返回后调用协作恢复。`state_change` 的 `supersede` 仍然只有 Full。模型仍是 `deepseek-flash`，执行器仍是进程。12 格验收通过之后才跑这 120 格。它是初步重复：10/10 的 Wilson 区间是 0.7225–1.0000，0/10 是 0.0000–0.2775。`state_change` 上 Full 与另外两臂的组内区间不重叠。四组加总之后的臂级区间重叠。没有 pilot 方差、目标效应和预注册，所以它不是确认性实验。

因此旧的 50% 与新的 10/40、20/40 同时成立。故障组不同，注入也有一处不同，不能合并。

## 送审时要留在正文里的不利结果

- 故障是预设的，不是自然生产分布。结论限于受测实现和这些故障。
- 模型只有 `deepseek-flash`。编码模型批次没有在容器里重跑。
- 协作式恢复盖不住外部写入者。内核读取窗口和内核级逃逸没有测。
- E1 的随机交错是这一次样本里提交先完成 64、撤销先发生 36。不写成固定比例。
- E6 的强制终止各是一次脚本化演示，不是 100 次样本。
- 旧 E7 只有 3 个批次。并发 1 的 p99 只有 3 个点。新 E7 的单位是 30 个批次中位数。
- 容器对照是确定性的发布端测量，不是另一批模型任务。
