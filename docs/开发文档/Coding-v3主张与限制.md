# Coding v3 主张与限制

这轮没有改历史 GO，没有改 v2 的原始 JSON，也没有改冻结稿。隐藏测试的通过标准没有降低。这台机器没有 Docker，所以没有任何一格把隐藏测试跑完。

## 可以支持的说法

工具链不再用“读两次就停止返回源码”或在工具 JSON 里夹带提交命令来阻止修复。开发集两格和确认集三格留下了可应用的 unified diff、SHA-256，以及读源码、修改、公开测试和测试后继续的轨迹。

在这些已经冻结的补丁上，通知送达时 B0 和 B1 接纳过期补丁，B2 和 B3 拒绝。通知缺失时四条臂都接纳，过期凭证为假。S3 上 B3 重放 Claim 字节，B2 没有这项恢复。黄金补丁走同一套臂，结果分开记录，不记成模型修好了仓库。

## 不能支持的说法

不能写编码任务的隐藏测试通过率，也不能写 Full 在编码任务上更可靠。容器没有启动，`container_tests_passed` 没有观测。宿主机摘出的失败行只作为模型可见现象，不是正式评分。

不能把开发集或确认集的 S1 差写成跨任务精度。开发集 2 对的区间半宽是 0.421，确认集 3 对的半宽是 0.354。配对差全是 1，区间退化，不使用零宽 bootstrap。确认状态是 `PRECISION_NOT_MET`。

不能把模型后继写成完成。五次后继观察都在预算内没有交出新补丁。

`b6dd92b` 不能单独复现这轮运行器。复现要同时使用 `freeze.json` 里的运行器哈希和协议哈希。

## 负结果和停止点

确认集 4 个任务里，1 个在 24 轮、40 次工具和 420 秒内没有形成补丁。形成补丁的格子也没有隐藏测试结论。按协议停止扩样。

研究定位停在受控 Runtime 的资格、过期凭证和效果恢复。编码能力这轮只证明工具循环可以产生并冻结补丁，不证明这些补丁通过隐藏测试。

## 补测之后可以写的数字

上面「不能写隐藏测试通过率」说的是补测之前。补测写在 `results/runtime/correctness/v3-coding/rescore/`，原 trace 里的 `docker_unavailable` 没有改。镜像 id 是 `sha256:6ff506466f8b1e981719b468cc0023b8ef000b983cdec0eafe119d01f379e31d`。

六个任务的初始树都失败，六份黄金补丁都通过。这是评分器自检。五份冻结补丁里 2 份通过隐藏测试，3 份未通过。确认集分母仍是 4，其中 `code-click-ac0e297e` 保持 `BUDGET_EXCEEDED`。按这个分母，确认集隐藏测试通过是 2/4。开发集是 0/2。

S1 拒绝侧的工作区没有通过隐藏测试。S3 五份恢复载荷都与冻结补丁一致；恢复字节是否通过，等于该补丁是否通过。未通过补丁的恢复不是编码成功。

运行器和协议的 LF 快照在 `results/runtime/correctness/v3-coding/artifact/`。两份文本 SHA-256 与 `freeze.json` 相同。模型是 `deepseek-flash`，温度 0。没有单独的 pip 锁。`b6dd92b` 仍然不包含这份运行器，在归档进入提交之前不能说这个 HEAD 单独复现 v3。

补测之后仍然不能写的是：Full 在编码任务上更可靠，S1 的 2/2 或 3/3 达到跨任务精度，模型后继已经完成，以及把 v4 的新调用并进这批数字。`dev-first-truncated/` 继续留在分母外面。
