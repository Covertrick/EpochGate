# M4–M6 Extension v2 协议

这份协议在 Coding 确认批的任何模型调用之前写定。`docs/开发文档/M4-M6独立确认协议.md` 和 `results/runtime/correctness/m6/summary.json` 里的 GO 保持原样，不因本文件改分类、改指标或改原始记录。E9、E10、E12 和普通 E4 样本不重跑。

v2 只处理三件事：Coding 家族此前没有初始失败测试；已有 `model_no_effect` 缺少可追溯分类；五个同值配对的零宽 bootstrap 不能当作跨任务泛化的精度证明。

## 历史结果的地位

履约家族已经跑完的 Pilot、确认批和 M5 是历史批次。它们的原始 JSON 不改。历史 GO 只说明：在当时写死的规则下，履约家族的条件子集达到了旧精度条文，并且 LangGraph 适配没有改内核。它不自动推广到 Coding 家族，也不把零宽区间写成未见任务上的总体精度。

## 假设

v2 不新开显著性声明。主要读数是描述和预先写明的精确区间，用来判断证据能不能支撑跨任务说法。

- 分配集：每个预先冻结的任务实例乘一个预先定义的故障，不论模型有没有交出效果。
- 条件子集：分配集里实际产生了工具效果、评分器也跑完的记录。
- 对照：B1 减 B2 的过期接纳，B3 减 B2 的已授权恢复。同一任务、同一故障、同一通知、同一效果边界。
- 分层：先按任务实例，再按家族。履约与 Coding 不合并成一个总成功率。

## Blocked 分类

只使用该格已经保存的字段。工具事件、模型原文或结束细节不在记录里，就标 `OUTCOME_UNKNOWN`。不允许事后调用模型来补标签，也不改原来的 `error_type`。

允许的标签：

- `MODEL_DID_NOT_ACT`：记录里有成功返回，且没有效果载荷，同时有工具轨迹或结束原因能说明模型没有提交。
- `CORRECT_ABSTENTION`：记录里有模型明确拒绝提交的原文。
- `TOOL_EXECUTION_FAILED`：记录里有工具执行错误。
- `MODEL_API_FAILED`：记录里有 HTTP、超时或密钥错误。
- `ENVIRONMENT_BLOCKED`：记录里有容器、评分器或仓库不可用。
- `OUTCOME_UNKNOWN`：以上证据都不够。

生成器源码里某条分支会在什么情况下写出 `model_no_effect`，只能放进敏感性分析，不能当成单格原始证据。

## Coding 候选

候选来自多个真实开源仓库的历史提交，不只一个仓库。每个候选要同时满足：

- 固定的 base commit。隐藏测试来自该历史里的真实测试改动，评分时才放进容器。
- 在 `python:3.10-slim` 里，只加隐藏测试时，指定测试失败。
- 加上该历史提交里的源代码修复后，同一测试通过。
- 代理可见工作区不含隐藏测试和评分器，工具也不能写这些路径。
- 能注入工作区版本变化、通知缺失或延迟、以及效果接收端中断。
- 终态由容器里的独立测试决定，不用 AST 常量代替。

仓库清单在筛选前固定为 markupsafe、itsdangerous、h11、packaging、more-itertools、click。看到结果之后不追加仓库。每个仓库只检查 `git log` 里从新到旧、同时改动测试文件和其余 Python 源文件的前 12 个提交。窗口用尽仍不足 6 个通过项，就停止。

进入条件按仓库名、再按 base commit 的字典序排列。可行性通过的前 2 个是 Pilot，紧接着的 4 个是确认批。再多的候选只留在预筛报告里，本轮不跑。通过数少于 6 时，不编造任务，不把已经通过的测试改成失败基线，状态写 `TASK_POOL_INSUFFICIENT`，确认批不启动。

镜像使用本机已有的 `python:3.10-slim`，图像标识 `sha256:6ff506466f8b1e981719b468cc0023b8ef000b983cdec0eafe119d01f379e31d`。可行性记录写出当时的 `docker image inspect` 标识。若运行时标识与此不同，该候选记为环境不一致，不进入矩阵。

## 执行预算

预算在看到 Pilot 或确认结果之前定死，不按正负结果加减次数。

- 可行性检查：不调用模型。
- Coding Pilot：2 个任务 × 4 臂 × 3 故障 = 24 次执行。
- 确认：仅当 Pilot 的环境门通过，且冻结清单里还有接下来的 4 个任务。4 × 4 × 3 = 48 次执行。
- M5：先对 1 个已经冻结的 Coding 任务做 2 模式 × 4 故障的冒烟。冒烟没有要求修改 LangGraph 内核，且同一容器能跑评分器时，才再跑清单里的下一个任务，最多再 8 次。总上限 16 次。
- 不设第三波，不补到每类 12 个实例。

Pilot 环境门只看执行是否成立，不看哪一臂更好：未阻塞格子里，容器评分和故障注入都要留下记录。若 Pilot 格子里超过一半是容器或评分器崩溃，确认批不启动。

S2 沿用旧规则：任务标识最后一个字符按 36 进制为偶数则通知缺失，否则延迟。四臂使用同一份模型提案和同一条事件时间线。

## 评分

容器独立测试通过、过期补丁是否进入最终工作区、合法后继是否完成、重复副作用、已授权效果是否恢复、工具调用数、输入与输出 token、端到端耗时。模型自述不算通过。

B2 与 B3 仍使用同一个效果接收端。B2 在一次决定里核对工作区版本并接纳补丁，不写 Claim，恢复为 `NOT_SUPPORTED`。B3 先提交补丁字节的 Claim，中断发生在接纳之前，恢复只重放 Claim 字节。

## 统计

每份 v2 报告同时给出五块，不能互相替代：

1. 全部分配的任务—故障实例。
2. 实际产生工具效果的条件子集。
3. blocked、弃权和失败的原因构成。证据不足保持 `OUTCOME_UNKNOWN`。
4. B1 与 B2、B2 与 B3 的匹配差。
5. 按任务实例和家族分开的结果。

五个或更多同值配对时，百分位 bootstrap 会收成零宽。这种区间记为退化，不作为总体精度证明。同时报告：

- 不一致配对上的精确 McNemar 检验。没有不一致配对时，不把检验说成显著。
- 各臂比例的 Clopper–Pearson 95% 区间。
- 失败数为 0 时的描述性上界 `1 - 0.05^(1/n)`。

精度设计目标：条件子集上，主要匹配差的精确区间半宽小于 0.25。半宽不小于 0.25，或确认配对少于 8，就写 `PRECISION_NOT_MET` 并停止。这不是“样本已经够了”的结论。半宽达不到时，预算也不允许加样本。

历史履约确认批的零宽 bootstrap 在本文件里重新描述为：样本内没有方差，不能支持跨任务泛化。`m6/summary.json` 的 `decision` 字段不改。

## M5

R0 只用 LangGraph 公开的检查点、中断和工具节点。没有 Claim 就写 `NOT_SUPPORTED`。R1 的去重属于外部接收端，字段 `capability_owner` 写 `external_receiver`。不修改 LangGraph 包内部。

冒烟要留下真实的工具或效果调用记录，并在同一镜像里跑隐藏测试。做不到，或只能靠改框架内核才测到，状态写 `PORTABILITY_LIMITED`，不补造完整的跨 Runtime 验证。

## 本轮决定

Extension 的通过条件不是全部测试通过。四条要同时成立：主要结果来自独立评分，四臂对照使用同一任务、通知和效果边界，每个失败或 blocked 有证据标签或明确的 `OUTCOME_UNKNOWN`，记录能追溯到 Git SHA、任务 SHA、镜像标识和原始 trace。

四条都成立，写 `GO_EXTENSION`。否则不继续加任务。投稿降级为：历史履约结果保留为小样本、同家族的机制观察；零宽区间不写成总体精度；Coding 若未进入，就不对编码任务作可靠性结论。本轮仍不改冻结稿。
