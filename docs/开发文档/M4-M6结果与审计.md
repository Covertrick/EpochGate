## H5

H5 是唯一事先指定的主要显著性声明。对比确认批里通知已送达的 S1，配对差是 B1 的过期接纳减去 B2 的过期接纳。未 blocked 的配对有 5 对：`ful-order-c1`、`ful-order-c2`、`ful-order-c3`、`ful-config-c4`、`ful-config-c6`。`ful-config-c5` 的 S1 没有模型效果，不进入这 5 对。

5 对的差都是 1。B1 五次都接受了过期凭证，B2 五次都没有。配对 bootstrap 使用种子 20261119、2000 次、百分位 2.5 和 97.5。均值 1.0，区间 1.0 到 1.0，半宽 0.0。半宽小于协议里的 0.20，点估计也大于 0.15 且区间在 0 的右侧。按协议的精度规则，这一项达到设计目标。

这 5 对内部没有方差，百分位区间因此收成一个点。它描述的是这 5 个已观察实例，不是未见任务上的稳定宽度。B2 在这 5 次里没有过期接纳。失败数为 0 时的保守上界是 `1 - 0.05^(1/5)`，约 0.45。不能把 0 次失败写成 100% 可靠。

S2 的 4 个未 blocked 实例上，四臂的过期接纳都是 0。通知缺失或延迟时，B1 与 B2 的差别没有出现。其中 3 个实例的物理文件不是事件之后的合法字节。这是状态可观测性边界，不是 H5 的主要对比。

## H4

H4 是次级结果。在同一 S1 任务上，四臂终态相同且过期接纳不同的比例是 2/5，也就是 0.4。这两条是 `ful-order-c3` 和 `ful-config-c6`。

另外三条的终态并不相同，所以没有进入这个比例，但终态和安全状态仍然不是一回事：

- `ful-order-c1` 和 `ful-order-c2`：B0 与 B1 的终态匹配为真，同时过期接纳为真。B2 与 B3 拒绝了旧凭证，终态匹配为假。
- `ful-config-c4`：B0 与 B1 过期接纳为真且终态不匹配。B2 与 B3 过期接纳为假，后继把终态做成匹配。

任务终态正确不能代表全部执行可靠性。这里没有只报一个总成功率。

## H6

H6 比较同一受控接收端上的 B2 与 B3，只看 S3 的已授权效果是否恢复。未 blocked 的配对有 4 对：`ful-order-c1`、`ful-config-c4`、`ful-config-c5`、`ful-config-c6`。每一对的物理摘要相同，接纳次数都是 1。B2 的 `interrupted_recovered` 为假，恢复字段是 `NOT_SUPPORTED`。B3 为真。配对差是 B3 减 B2，4 对都是 1，bootstrap 区间同样收成 1.0。这是次级结果，不另做多重比较惩罚。

B2 在同一次决定里检查版本并接纳，没有 EpochGate Claim，也没有“已授权但未发布”的恢复。B3 先提交 Claim，再把 Claim 字节交给同一个接收端。两臂的物理摘要相同，说明这 4 对的差别在恢复，不在两套不同的发布器。

结果在 `results/runtime/correctness/m5/`。LangGraph 包内部没有改，EpochGate 运行时内核也没有改。`kernel_modified` 为 false。适配只使用公开的 `StateGraph`、`MemorySaver` 和 `interrupt`。

履约家族 3 个新实例、R0/R1、四类故障，24 格。编码家族没有进入。`ful-config-m3` 除 `notice_missing` 以外的 6 格是 `model_no_effect`。其余 18 格可观察，覆盖率 0.75。`NOT_SUPPORTED` 不是机制失败。
