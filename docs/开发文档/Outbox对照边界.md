# Outbox 对照边界

`scripts/outbox_baseline.py` 是同库事务性效果基线，不是 EpochGate 的弱化实现，也不是覆盖全部效果合同的强外部基线。

它在一个 SQLite 事务里做两件事：版本仍等于调用方持有的 token，以及按效果键插入一行。同键同载荷回放，同键不同载荷冲突，旧 token 拒绝。记录在 `results/runtime/correctness/outbox-baseline/summary.json`。

## 同一效果合同下可以比较的性质

合同限定为：效果是数据库里的一行，版本和插入由同一个 SQLite 事务提交。

在这个合同里，Outbox 与 Full 的受控接收端相同的是：旧凭证不留下新行，同键同载荷不第二次插入，同键不同载荷不覆盖旧行。这些性质不能写成 Full 的算法优势。B2 把版本检查和 `SharedReceiver.accept` 放在同一进程锁里，也落在这一类。

## 这个基线没有实现的性质

文件发布不在这个合同里。Outbox 没有 Claim，没有私有文件、`os.replace` 和回执。因此它不提供 Claim 到物理字节的绑定，也不能在替换之后、回执之前把结果分成已发生和 UNKNOWN。

协作恢复不在这个合同里。两个恢复者、Claim 之后进程退出、回执丢失后的核对，都没有对应实现。不能因为 Outbox 没有这些恢复，就说它全面更不可靠。

## 不适用于这个基线的保证

缺通知时，Outbox 不能推断外部世界已经变化。任意 HTTP 或不受控外部写入也不是 exactly-once。这两条 Full 同样没有。

## 成本

这次对照没有和 E7/E8 使用同一配置，不比较耗时。环境是本机 SQLite，不是容器发布。

若要声称 Full 优于现有事务式执行，仅这一份对照不够。可以写的是：不同接收端提供不同保证；EpochGate 把协作文件发布和恢复证据放进了受控评估。
