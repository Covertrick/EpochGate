## 语义

文件发布的决定点是 `claim_publish` 成功提交。Claim 前撤销则不发布。Claim 已经提交之后的撤销不撤回这次发布。`os.replace` 不放进 SQLite 事务，因此替换后、回执前的进程死亡靠文件摘要对账，不把锁内替换说成崩溃原子性。

版本权威是 RunLedger 那一个数据库。`supersede(run, sink)` 在账本事务里用 SQL 自增 token 和 `state_version`，并写下 `pending_sink_epoch`。EffectSink 只保存接纳行和一份版本镜像。镜像没写上时，下次 `repair_sink` 或提交前补齐，这个补齐不接纳效果。`supersede(run)` 仍然只推进 Run，合法后继继续因版本不齐被拒绝。

## 修复前和修复后

| 项 | 修复前 | 修复后 |
| --- | --- | --- |
| 两次并发 `supersede` | 12/12 最终 token 为 2，两次调用都返回成功 | E1 的 100 次最终 token 都是 3，丢更新 0 |
| 重启后的 sink 版本 | 回到 1。旧 token 被拒，合法后继也被拒，接受次数 0 | 重启后镜像为 2。旧 token 拒绝率 1，合法后继完成率 1 |
| 同键不同 payload | 返回 `replayed`，不报告冲突 | 返回 `conflict`，原 payload 保留，接受次数不增加 |
| Claim 后、替换前撤销 | 文件仍写成 `order 3` 并写回执 | 行为保持。事件顺序是 `intent_recorded`、`publish_claimed`、`file_published`。这是决定点之后的发布，不是契约违反 |
| Claim 前撤销 | 文件不出现 | 仍不出现 |

版本推进中途让镜像写入失败时，接受次数是 0。补齐镜像之后，旧 token 仍被拒绝，后继可以完成。未对齐的 `supersede(run)` 之后，后继仍然被 `reason=version` 拒绝。

## E1 并发安全与进展

每个场景 100 次。随机交错没有用 barrier 规定先后。延迟单位是秒。

| 场景 | 结果 |
| --- | --- |
| 先撤销后提交 | 100/100 拒绝，接受次数 0 |
| 先提交后撤销 | 100/100 第一次完成，后续提交拒绝，receipt 仍在 |
| 两进程同时 `supersede` | 丢更新 0，最终 token 只有 3。p50 0.0178，p95 0.0190，p99 0.0811 |
| 多进程同键同载荷 | 100/100 状态为 `completed` 与 `replayed`，接受次数 1 |
| 不同键并发 | 100/100 两边都 `completed`，接受次数 2 |
| 对齐 supersede 后的后继 | 100/100 旧提交拒绝、新提交完成，接受次数 1 |
| 撤销与提交随机交错 | 提交先完成 64，撤销先发生且接受次数为 0 的 36。提交延迟 p50 0.0064，p95 0.0213，p99 0.0332 |

旧 token 在「先撤销」和「对齐后继」里的接纳次数是 0。新 token 的合法完成率在对齐场景是 100/100。随机交错不能写成固定比例，这里只报告这次样本。

## E2 两个独立指标

| 状态 | Stale Rejection Rate | Eligible Successor Completion Rate |
| --- | --- | --- |
| 正常对齐 | 1 | 1 |
| 只重启控制进程 | 1 | 1 |
| 版本推进中镜像失败后再补齐 | 1 | 1 |
| 四进程并发推进，20 次 | 1 | 1 |

并发推进的丢更新是 0。未对齐后继被拒绝，这一格不并进上表的完成率。镜像失败期间的接受次数是 0。重启后读到的 sink 版本是 2。

## E3 文件发布窗口

| 时刻 | 观察 |
| --- | --- |
| Claim 前撤销 | `published=false`，目标文件不存在 |
| Claim 后、替换前撤销 | claim 状态 `claimed`，文件字节 `order 3`，回执写上。事件含 `publish_claimed` 然后 `file_published` |
| 替换后、回执前再打开账本 | 第一次对账 `completed`，第二次 `replayed`，字节仍是 `order 3` |
| 回执之后 | 第二次对账是 `replayed`，不再次改文件 |

撤销和替换的合法顺序由 claim 是否已经提交决定。替换后的强制终止放在 E6，它不是磁盘掉电。

## E4 真实工作流

360 格都已评分。命令是 `python -m uv run python scripts/runtime_e4_matrix.py`。模型是 `deepseek-flash`。Node 是本机 `node-v24.13.0`。汇总在 `results/runtime/correctness/after/e4_summary.json`，每格原始记录在 `results/runtime/correctness/after/e4/cells/`。

这台机器没有 WSL，`docker_available` 是 false。三类任务都走进程执行器。编码任务不进入 eg-alpine。`bug.py` 的终态用语法树读取 `value()` 的返回整数，不采用模型自己说的成功。库存看 `order.txt` 是否等于当时的 `stock.txt`。审批看 `decision.txt` 是否等于当时的 `rules.txt`。

三臂是 `direct`、`commit_only`、`full`。`direct` 和 `commit_only` 在发布门之后直接写文件。`full` 走 claim 和 `os.replace`。故障在发布门打开时注入：库存把库存从 3 改成 0，审批把 ALLOW 改成 DENY，编码把 `spec.txt` 从 1 改成 2。`state_change` 和 `concurrent_edit` 的 full 臂调用对齐的 `supersede`。`permission_revoked` 和 `publish_failure` 的 full 臂调用 `revoke`。`version_mismatch` 和 `stale_credential` 的 full 臂只调用 `supersede(run)`，不推进 sink。`receipt_loss` 的 full 臂在 claim 成功后、`os.replace` 之前返回，然后对账。`missing_notice` 只改库存，不发 supersede。

`retry` 让模型对同一内容写两次。`direct` 和 `commit_only` 每次多出 3 次 `eg_write`，10 次合计 30。`full` 只有一条 completed 效果，第二次是同一键的重放，重复写入计 0。

`version_mismatch` 和 `stale_credential` 的 full 臂把 Run token 从 1 增到 2，sink 镜像留在 1。文件发布核对的是 Run token，不是 sink 版本，所以后继文件仍然落地。这组不能用来说明未对齐的 sink 拒绝了效果。sink 拒绝留在 E2。`stale_credential` 没有改 `spec.txt`，所以 direct 写成 `return 1` 也算终态正确。

## E5 效果身份与 UNKNOWN

| 检查 | 结果 |
| --- | --- |
| 同键同载荷 | `replayed`，接受次数 1 |
| 同键不同载荷 | `conflict`，保存的 payload 仍是第一次的 |
| 重启后再用不同载荷 | 仍是 `conflict` |
| `SystemExit(86)` 于接纳之后、回执之前 | 对账 `confirmed_from_sink`，随后不同载荷是 `conflict`，接受次数 1 |
| 外部不可查询 | `seal_unconfirmed_external` 为 `unknown`，再次提交也是 `unknown` |
| 本地 HTTP 响应在接纳后断开 | 客户端得到 `RemoteDisconnected`。同一载荷再请求是 `replayed`。不同载荷是 `conflict`，保存的仍是 `once` |
| 本地 HTTP 返回不可用 | 客户端得到 `HTTPError`。没有把这次记成成功，也没有自动改用别的结果 |

这只划定这个本地接收端的边界。它不是任意 HTTP 服务的 exactly-once。

## E6 强制终止

| 种类 | 结果 |
| --- | --- |
| 受控 `SystemExit(86)` | 对账 `confirmed_from_sink`，接受次数 1 |
| `TerminateProcess`，sink 已接纳、账本还没有效果行 | 重开后对账 `confirmed_from_sink`，接受次数仍是 1 |
| 未提交的 SQLite 事务里把 token 改成 99，然后杀掉进程 | 重开后 token 仍是 1 |

`TerminateProcess` 不是突然断电，也不是磁盘持久性证明。
