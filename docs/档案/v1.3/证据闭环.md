# EpochGate v1.3 P0：证据闭环

日期：2026-11-02。包版本仍是 **1.2.0**。这次只订正已经写出的数字和取消语义，没有重跑真实 API，也没有把历史确认性 JSONL 改记成新版本。

原始行仍在 [`results/real/phase_f/confirmatory/f1_m_confirmatory.jsonl`](../../../results/real/phase_f/confirmatory/f1_m_confirmatory.jsonl)，代码基线仍是 `8579d2b`。独立重算结果在 [`results/real/phase_f/audit/v1_3_f1_recompute.json`](../../../results/real/phase_f/audit/v1_3_f1_recompute.json)，由 [`scripts/audit_stage_f_evidence.py`](../../../scripts/audit_stage_f_evidence.py) 只读该 JSONL 生成。它不导入 `analyze_stage_f`。

## 1. F1 主结果怎么算出来

465.2 和 3.6981 s 可以从原始行重算，而且和 [`f1_m_mechanism.json`](../../../results/real/phase_f/summary/f1_m_mechanism.json) 一致。

主结果是三个预先指定单元 `long_early`、`long_mid`、`mid_mid` 里面，双臂都触发（`both_triggered`）的配对差，按配对等权。纳入的 5 个配对是：

| 配对 | 文本差 | 槽位差 (s) |
| --- | ---: | ---: |
| `long_early` seed 5551 | 631 | 4.9431 |
| `long_early` seed 5552 | 473 | 4.4592 |
| `long_mid` seed 5651 | 450 | 3.3937 |
| `long_mid` seed 5652 | 547 | 3.9282 |
| `mid_mid` seed 5452 | 225 | 1.7663 |

文本均值 (631+473+450+547+225)/5 = **465.2**，中位数 **473.0**。槽位差先按配对四舍五入到 4 位小数再平均，均值 **3.6981 s**，中位数 **3.9282 s**。报告里的 3.70 s 就是这个 3.6981 s。

`mid_mid` seed 5451 没有进入均值：A 臂是 `trigger_late`，B 臂是 `triggered`，配对状态是 `B_only_triggered`，条件差记为空。

各单元只对纳入配对求均值：

| 单元 | 纳入配对 | 文本均值 (SD) | 槽位均值 (SD) |
| --- | ---: | --- | --- |
| `long_early` | 2 | 552.0 (111.72) | 4.7012 s (0.3422) |
| `long_mid` | 2 | 498.5 (68.59) | 3.6609 s (0.3779) |
| `mid_mid` | 1 | 225.0（无 SD） | 1.7663 s（无 SD） |

把这三个单元均值再等权，得到文本 **425.1667**、槽位 **3.3761 s**。这是对照统计量。主结果仍然是上面的 5 配对均值。

订正前的阶段 F 文档把 `mid_mid` 写成 198.0 词元和 1.478 s，再把三个单元等权，会得到约 **416.17** 词元和 **3.28 s**。那张表和当前 JSONL 不一致。416.17 解释了外部评估里的另一套算法，它不是这次重算的主结果。阶段 F 文档里的 F1 表已经改成与 JSONL 一致，包括原先也不一致的 `long_late`、`short_mid`、`short_late`。

先前写出的 95% 区间 [334.40, 567.80] 和 [2.63, 4.55] s，是对这 5 个配对差做重采样。重采样单位是配对差，不是把同一对的 A、B 两行拆开。n=5，单元内部只有 2 个或 1 个配对。这个区间描述已观测配对，不能当成稳定的总体估计。

## 2. Holm 检验没有做

`analyze_stage_f.py` 里的 `holm_bonferroni_primary_cells` 只是三个单元的名字。全仓库没有 Holm、t 检验或 Wilcoxon 的 p 值。预先指定主单元，和“已经做过多重比较校正并显著”，是两件事。文档里“经 Holm-Bonferroni 后显著”已删去。

## 3. 词元计数规则

[`stage_e_runner.py`](../../../src/epochgate/stage_e_runner.py) 的 `_text_for_attempt` 只拼接同一 attempt 的 `token_delta` 文本，再交给 [`text_tokens.py`](../../../src/epochgate/text_tokens.py) 的 `tiktoken` / `cl100k_base` 做一次编码。工具参数和 `tool_call_delta` 不进入这个计数。撤销后的窗口是该 attempt 上时间不早于撤销时刻的 `token_delta`。

确认性 JSONL 只保存计数，不保存拼接后的原文，所以不能从结果文件重新分词。这次审计核对的是代码路径。纳入的 5 对里，B 臂撤销后的文本词元计数都是 0。

## 4. F3：`aclose()` 不是供应商取消确认

B 臂在 `stop_on_cancel=True` 时调用 `response.aclose()`。这只表示客户端关掉了正在读的响应。能力位现在分开写：

| 字段 | B 臂 | A 臂 |
| --- | --- | --- |
| `local_read_abort` | 真 | 假 |
| `client_stream_close_issued` | 真 | 假 |
| `transport_disconnect_observed` | 假 | 假 |
| `provider_cancel_api_invoked` | 假 | 假 |
| `provider_cancel_ack_received` | 假 | 假 |
| `provider_cancel_request` | 假 | 假 |
| `provider_cancel_ack_semantics` | `UNKNOWN` | `UNKNOWN` |
| `server_generation_stopped_observed` | 假 | 假 |
| `server_resource_reclaim_observed` | 假 | 假 |

A 臂以前把 `provider_cancel_ack_semantics` 写成 `ACKNOWLEDGED`，那只是本地接受了“继续读”的策略。现改为 `UNKNOWN`。非流式 `HttpToolBackend` 仍是未调用供应商取消 API。不支持取消的 `FakeBackend` 仍是 `NOT_SUPPORTED`，同样没有调用供应商取消 API。

[`f3_capability_contract.json`](../../../results/real/phase_f/summary/f3_capability_contract.json) 已按当前代码重写合同表。里面嵌着的 seed 8101、8102 探针行仍是当时的记录，旧的 `capabilities_6d` 没有改。`results/real/phase_f/confirmatory/` 下的 JSONL 也没有改。
