# v0.4 测试记录

日期：2026-10-29。代码版本 0.4.0。下面的数字只用来核对机制是否按声明工作。它们不是性能结论，也不能写成模型或库存服务的耗时承诺。

取消回执仍然只表示客户端见到的事实。它不是 GPU 已释放，这次也没有把它当成已解决项。

## 测了什么

离线套件 `python -m uv run pytest -q`：46 项通过，不访问外网。其中 `tests/test_smoke_checklist.py` 覆盖清单里不需要模型的部分，包括正概率却零故障时 cell 无效。

联调清单由 `epochgate http-smoke` 真正执行，不再只打印一次工具调用。

| 检查 | 预期 | 这次怎么验 |
| --- | --- | --- |
| 故障注入 | 种子 42、6 次请求，trace 里有 `fault_injected` 和 `fault_kind`；条数与计划一致 | `results/v0.4/trace.jsonl` |
| 正概率零故障 | cell 标为无效，退出码非 0 | 同一次报告的 `cell_valid` |

两种启动都用过。清单里的 ASGI 直连由离线测试和 `reproduce` 覆盖。联调另起了 `epochgate env-serve --host 127.0.0.1 --port 8080`，smoke 用 `--env-url http://127.0.0.1:8080`。`--base-url` 如果传入，覆盖的是模型地址，不是库存端口。

密钥放在仓库根 `.env`，变量名是 `EPOCHGATE_BASE_URL`、`EPOCHGATE_API_KEY`、`EPOCHGATE_MODEL`。命令只把它们读进当前进程。`results/v0.4/manifest.json` 里这三项都是 `set`，没有值。结果目录里没有密钥。

## 怎么跑

```powershell
python -m uv run epochgate env-serve --host 127.0.0.1 --port 8080 --db traces/inventory.sqlite
python -m uv run epochgate http-smoke --env-url http://127.0.0.1:8080 --chaos scenarios/chaos.yaml --seed 42 --out results/v0.4 --requests 6
python -m uv run epochgate http-smoke --env-url http://127.0.0.1:8080 --chaos scenarios/chaos.yaml --seed 42 --out results/v0.4/prior-rerun --requests 1 --service-prior 1.1003808000488204
python -m uv run epochgate reproduce --cell-id checks-seed-42-none --manifest results/v0.4/manifest.json --out results/v0.4/reproduce
```

`scenarios/chaos.yaml` 的延迟是 2–8 秒，概率分别为延迟 0.3、取值故障 0.2、崩溃 0.1。离线测试不用这份时长。

## 结果

主运行退出码 0。`cell_valid=true`，`checks_passed=true`。原因是 trace 条数和计划掷出的故障一致。

种子 42 的 6 次请求里，5 次注入了故障，顺序是：

| 请求 | fault_kind | 说明 |
| --- | --- | --- |
| a0 | value_fault / empty_tool_calls | 没有打到模型，不计入服务时间 |
| a1 | latency_spike | 注入 3.143 秒，样本已减去这段 |
| a2 | 无 | 正常请求 |
| a3 | latency_spike | 注入 5.456 秒 |
| a4 | latency_spike | 注入 2.767 秒 |
| a5 | latency_spike | 注入 6.139 秒 |

清单全部通过：200 行、close 后写入失败、成交 1 次且库存 0、同一 action 的 commit id 只有 1 个且库存为 3、默认路径没有检查-写入间隙、`window_s>0` 时出现版本冲突、strict/loose 租约为 5 秒和 30 秒、先验 0 的任务成功、估计超时的任务被拒绝且没有 `backend_request`。真实库存服务的 commit id 是 `cmt-05e4c9d40c16`，重复提交没有再次扣减。

服务时间样本是墙钟减去已记录的注入延迟。取值故障没有样本。五个样本的统计量：

| 指标 | 秒 |
| --- | --- |
| max | 1.154 |
| p50 | 1.100 |
| p95 | 1.150 |
| p99 | 1.153 |
| Gini | 0.065 |

完整浮点在 `results/v0.4/service_prior.json`。p50 被写回先验，同一轮又跑了一次不可达拒绝：先验 1.100 秒时，截止时间更早的任务被拒绝，另一笔任务成功。

第二轮把 `--service-prior` 设成这个 p50，只发 1 次请求。种子 42 的第一次掷骰是 value_fault，所以这轮自己的样本是空的，`measured_p50=0`，但准入检查用的是传入的 1.100 秒，超时任务仍被拒绝。`cell_valid=true`，因为这 1 次请求确实记下了故障。记录在 `results/v0.4/prior-rerun/`。

`epochgate reproduce --cell-id checks-seed-42-none` 只重跑了本地检查 cell，输出是 `tasks=10 on_time=10 fault_rate=0.000`。没有再次请求模型。模型 cell 的 id 是 `smoke-seed-42-chaos`，它的故障序列由种子决定，首次 trace 已经和计划一致。
