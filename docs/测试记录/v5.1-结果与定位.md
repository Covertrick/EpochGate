# v5.1 结果与定位

日期：2026-11-04。封存确认性 sha256 仍是 `f5277e8f61945f50db68267f0ff78fbd648cb553833ec51ca86d6d0a89c9bc39`，7000–7049 没有被改写。

## 判决

不以 5.0 的当前主张发表。独立时间窗口没有复现高负载上的正差。本机 vLLM 只做了四组一次对照：本地多握 1.5 秒槽，旁观者就晚 1.5 秒开始，而这 1.5 秒里引擎 running 已经是 0；abort 计数没有增加，KV 占用没有被这次采样记下来。这能分开「本地槽」和「这一台上的引擎占用」，不能证明 M0 解释不了的新机制，也不能证明新算法。

中负载在新窗口里两道工程门槛仍过，但区间比开跑前要求的 0.25 秒宽得多，而且 G0 槽等待基线从大约 4.2 秒升到 11.2 秒。它不能单独把双负载结论救回来。

## 四步分别得到了什么

阶段 A 通过。50 对 × 两档负载完整，bystander 都是独立 task 但共用两个本地槽，P95 与 10000 次配对 bootstrap 能重算出已发表数字。服务端状态全部是 `unknown`。`max_tokens`、temperature 和墙钟没有写进旧 JSONL；运行器 prompt 用的是 “about {words}”，协议模板写的是 “exactly {words}”。

阶段 B 的高负载没有同向再现。高负载端到端也不在 10% 附近，点估计是 0.2%。中负载同向为正，区间半宽约 1.2 秒，没有达到冻结协议里的 0.25 秒精度。

阶段 C 在本机 RTX 4060 上跑了真实 vLLM，和先前的脚本校准分开。引擎是 Windows 轮子 0.32.0，模型 Qwen2.5-1.5B-Instruct，fp16，Triton attention，eager。四组各一次，详见 [v5.1-vLLM四组.md](./v5.1-vLLM四组.md)。G2-hold-slot 把本地槽多留 1.5 秒，bystander-0 拿到槽的时刻从 0.281 秒变成 1.797 秒；这段时间 `num_requests_running` 为 0。`finished_reason=abort` 始终是 0，断流请求也没有计入 `stop`。KV 曲线这次没有采到。脚本校准里 G2-residual 的 0.05 秒仍是注入的，不能当成这次 vLLM 的残余。

阶段 D 的 M0 在本批中负载拟合（α=2.584，β=−7.803），预测高负载的平均残差是 −1.98 秒，区间不含 0。这是过预测：高负载没有出现中负载那条直线所描述的正差。M1/M2 因没有可观测后端残余而没有拟合。Retire（arXiv:2610.01160）的主指标是 revision-to-successor TTFT 和 KV 继承，并报告无关租户运行时间变化约 1%。指标和条件与本文不同，所以不能把 Retire 的句子换成本文贡献，也不能保留「首次」。

## 合同第 8 节对上的那一行

DS 不能按预登记的双负载结果复现。本机 vLLM 显示本地握槽可以在引擎已经空闲时继续挡住下一条独立请求，但没有出现可重复、且 M0 解释不了的后端残余。定位仍是：不以当前主张发布 5.0 论文。
