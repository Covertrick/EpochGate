# 真实 API 测试记录

日期：2026-11-02。模型地址 `https://api.deepseek.com/v1`，模型名 `deepseek-chat`。密钥只在进程环境里，原始行里没有。

这轮测两件事：静态预约是否能由真实模型完成，以及生成过程中库存变为 0 之后，客户端还能不能少收后续增量。测的是客户端已经收到的增量、本地读循环是否停下，以及网关有没有提交。`response.aclose()` 只断开本地的读。它不表示供应商少计费，也不表示 GPU 已停。取消之后服务端还算了多少，记为未知。

离线套件 `uv run pytest -q` 这次是 95 项通过。那些测试不访问这个模型。`tests/mocks/` 里的 `MockStreamingBackend` 只给 CI 用，不写入下面的数字。

## 静态预约

命令：`uv run epochgate static-reserve --runs 6`。

无外生变化。起点库存 3。目标是调用 `reserve`，参数 `qty` 为整数 1。解析失败时同一请求最多再试一次。六次都是第一次就解析出工具调用。

| 次序 | 工具 | 参数 | 是否提交 | 库存 | 重试 |
| --- | --- | --- | --- | --- | --- |
| 1–6 | reserve | `{"qty": 1}` | 是 | 3 → 2 | 0 |

六次都成功。原始行在 `results/real/baseline.jsonl`，同一内容也在 `results/real/static_runs.jsonl`。这是真实模型能力基线：这个提示词和工具 schema 下，`deepseek-chat` 能给出可解析的 `tool_calls`，网关能提交，库存能从 3 变成 2。没有重试。

## 流式 A/B

触发是收到第一个增量之后 0.3 秒，把库存改为 0。不看工具名。

先用「一句话再调用工具」探过到达间隔。18 个增量在 0.210 秒内到齐，0.3 秒的回调还没执行，流已经结束。那 6 行在 `results/real/paired_short.jsonl`：`stock_change_fired` 为 false，两臂都提交成功，库存停在 2。这次不能用来比较截断。

正式三对把任务改成先写至少 180 词，再调用 `reserve`。同一条 0.3 秒规则落在生成还在继续的时候。命令：`uv run epochgate stream-ab --pairs 3 --delay 0.3`。原始行在 `results/real/paired.jsonl`。

A 臂资格撤销后不关连接。B 臂调用 `response.aclose()`。本地增量计的是客户端收到的 `token_delta` 和 `tool_call_delta`，`usage_source` 都是 `local`。三对是个案，不写置信区间，也不写显著减少。

| 种子 | 臂 | 撤销时已接收 | 撤销后额外增量 | 该次读循环跨度 | 是否提交 | 旧结果是否送到网关 | 本地读循环是否停止 | 期末库存 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | A | 42 | 294 | 2.354 秒 | 否 | 是 | 否 | 0 |
| 1 | B | 43 | 0 | 0.304 秒 | 否 | 否 | 是 | 0 |
| 2 | A | 45 | 156 | 1.550 秒 | 否 | 是 | 否 | 0 |
| 2 | B | 32 | 0 | 0.303 秒 | 否 | 否 | 是 | 0 |
| 3 | A | 37 | 210 | 1.917 秒 | 否 | 是 | 否 | 0 |
| 3 | B | 38 | 0 | 0.306 秒 | 否 | 否 | 是 | 0 |

B 臂三次 `local_stop_latency_s` 是 0.00811、0.00802、0.00817 秒。证据文本是「本地循环已停」。A 臂没有这个时刻。

撤销前的增量不是同一个数。真实模型每次吐出的分片数不一样，不能把 42 和 43 说成对齐。

两臂最终都没有 `action_committed`。种子 1 的 A 臂任务状态是 `failed`，其余五次是 `rejected`。库存都以 0 结束。

B 臂被撤销的那一次没有再向本地交出增量。后面的重规划仍然在生成：A 的 `replan_tokens` 是 290、312、301，B 是 308、163、331。立刻停止去掉的是被撤销那一次的后续增量，没有去掉后来重新发起的那一次。

## 供应商用量

行里的 `provider_usage` 是整条 trace 里最后一次出现的供应商 usage。B 臂切断之后又重规划了一次，所以这个对象不能当成被切断那次请求的账单。被切断那次在服务端还生成了多少，仍然未知。

A 臂三次最后见到的 `completion_tokens` 是 365、341、330。B 臂是 337、192、360。这些数里混有重规划。它们不能用来写「断开连接省下了供应商的 completion」。能写的是：被撤销的那一次，客户端在撤销后多收的增量是 294/156/210 对 0/0/0。

## 四个问题

真实模型能否稳定完成一笔静态库存预约：能。六次都是 `reserve`、`qty` 为 1、网关提交、库存从 3 到 2，重试次数是 0。

生成期间能否看到外生状态变化：能，只要生成还没在 0.3 秒内结束。短回复在 0.210 秒内结束，回调没有发生。180 词的回复里，六次都在首个增量后 0.3 秒把库存改为 0，并且都出现了资格撤销。

相对「只拒绝迟到结果、生成继续」，资格撤销后立刻停止是否减少了本地可见的失效生成：在这三对里，被撤销的那一次在撤销后又收到的本地增量，A 是 294、156、210，B 是 0。A 的这些增量发生在资格撤销之后，旧结果被送到网关并被拒绝。B 的同一次尝试没有再产出增量，本地读循环在约 0.008 秒内停下。两臂后来都有上百个重规划增量。

主实验还缺什么：被切断那一次的供应商账单，以及服务端在 `aclose` 之后还算了多少。这三对没有置信区间。变化间隔相对真实推理中位数的校准，这次只做到「0.3 秒能落在 180 词回复的中途」，没有做一组间隔扫描。

有统计证据的结论：没有。上面的增量都是三对个案。
