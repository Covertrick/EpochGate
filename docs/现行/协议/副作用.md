# 副作用协议

可控制的接收器把幂等键、版本和 receipt 写在自己的 SQLite 里。`commit_authorized` 在 RunLedger 的同一把锁里核对 fencing token 并调用接收器。

因此有两种结果：

- 撤销先完成：旧 token 被拒绝，接收器接受次数是 0。
- 提交先完成：接收器接受 1 次，随后的重复调用返回原来的 receipt。

这个保证只覆盖进入这把锁的接收器。普通 HTTP 工具如果已经把请求发出去，本地 token 比较不能把它收回。那种情况保持 `OUTCOME_UNKNOWN`，不自动再执行。

同一进程里的线程用这把锁。两个进程共用一个 SQLite 文件时，提交和撤销各自执行 `BEGIN IMMEDIATE`，由数据库写事务排队。`gpu_reclaimed=false` 只表示这个布尔位没有被写成 true；后端观测列是 `not_observable`，不能把它读成“已经证明没有回收”。

文件发布先把暂存内容的 SHA-256 记成 `DISPATCHED`，再移动文件，然后重读摘要。摘要一致才写 `file_published`，并且 `receipt_verified` 为 true。移动之后、receipt 之前进程消失，恢复用磁盘上的摘要完成同一次声明，不第二次写入。摘要对不上就停在 `OUTCOME_UNKNOWN`。

`chain_completed` 只表示预期路径有一条核对过的发布。`repair_demonstrated` 还要基线失败、独立评分通过。只有 `eg_read` 的记录两者都是 false。
