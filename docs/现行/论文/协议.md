# 实验协议

日期：2026-11-10。这三项问题是这篇预印本的范围。不研究 GPU 回收，不宣称任意 HTTP 的 exactly-once，不报告 SWE-bench 修复率。

## 研究问题

| 问题 | 要回答什么 |
| --- | --- |
| RQ1 撤销 | 外部状态变了以后，旧动作能否提交？对齐的新资格能否完成？ |
| RQ2 恢复 | 崩溃和未确认窗口里，能否分出未生效、已生效和未知？ |
| RQ3 开销 | 同样一次模型调用、同样一份 sink 载荷，账本和对账多花多少时间？ |

取消到进程退出只作为 RQ2 的进程证据，不延伸成资源回收结论。

## 版本协调规则

一条提交合法，需要三件事同时成立：fencing token 等于 Run 的当前 token，调用方带上的 `state_version` 等于 Run 的当前版本，sink 的版本等于这个 `state_version`。

`supersede(run, sink)` 在同一把锁里把 token、Run 版本和 sink 版本一起加一。这是对齐通知。旧 token 必须被拒绝，新 token 必须可以提交。

`supersede(run)` 只推进 Run，不推进 sink。按上面的规则，新 token 也会被版本检查拒绝。这记为协调缺陷，不记为安全拒绝。

没有调用 `supersede` 时，外部库存自己变化不会使旧 token 失效。

`revoke` 取消整条 Run 的资格。它不提供后继动作。

## 实验包

| 包 | 做什么 | 重复 |
| --- | --- | --- |
| A | `deepseek-flash` 按库存回复一行 `COMMIT`，再交给 RunLedger | 三个通知条件各 1 次 |
| A-DSH | 同一条 DSH 会话里读 `stock.txt`、写 `order.txt`。`EG_PUBLISH_GATE` 把第一次写入停在 reserve 和 publish 之间 | 没有通知 1 次，对齐 `supersede` 1 次 |
| B | 10 个机制不同的确定性场景 | 每个 5 次 |
| C | B0/B1/B2 交错，种子 20261110 | 每臂 20 次，并发 1 |
| D | 四个崩溃点、短睡眠进程取消、撤销和提交并发 | 崩溃 3 次，取消 8 次，竞争 20 次 |

B0 只做 sink 版本检查。B1 调用 `commit_authorized`。B2 在 B1 之后重新打开 SQLite 并读取 receipt。三臂的模型提示和载荷都是 `OK`。这里不先调用 `record_intent`：意图把效果标成 `started` 之后，`commit_authorized` 会停在 `unknown` 并不写 sink。那是另一条未确认窗口，放在包 B，不放进开销表。

## 不在范围内

500 条 SWE-bench、新的 fencing 算法、GPU 或 KV 回收、内核逃逸、任意第三方 HTTP 的 exactly-once、把 n=20 写成 P99。
