# 恢复

故障发生在独立进程里，退出码 86。恢复进程重新打开 SQLite，再看接收器里有没有行。

| 故障点 | 决策 | 接收器接受次数 |
| --- | --- | --- |
| 派发前 | `not_applied` | 0 |
| 接收器写入前 | `not_applied` | 0 |
| 接收器写入后、receipt 持久化前 | `confirmed_from_sink` | 1 |
| receipt 已持久化 | `replay` | 1 |

`not_applied` 的证明是这只可控接收器没有行。对一个可能已经收到请求、却没有查询接口的外部系统，同样的空档应保持 `OUTCOME_UNKNOWN`。

2026-11-10 又补了四类进程级故障，证据在 `packages/runtime/tests/test_fault_recovery.py`。同一套全量里还有进程树和文件发布中断：`test_grandchild_keeps_slot_until_it_exits`、`test_crash_after_move_reconciles_the_same_digest_once`。

| 故障 | 观察到的结果 |
| --- | --- |
| `BEGIN IMMEDIATE` 已把 fencing token 改成 99，进程在提交前被杀掉 | 重新打开后 token 仍是 1 |
| 控制服务创建 Run 之后进程被杀掉 | 新进程打开同一 SQLite，token 和 `running` 还在 |
| 租约上的 PID 仍活着 | `reconcile_dead_workers` 不释放 |
| 该 PID 退出之后再对账，并对账第二次 | 第一次释放这一条租约，第二次为空 |
| 文件已经换到目标路径、receipt 还没写 | 按目标文件摘要补上同一次 claim；再对账是重放 |
| 可控接收器已有行，账本停在启动后 | 第一次 `confirmed_from_sink`，第二次 `replay`，接受次数保持 1 |

这些都是本机可查询的账本、接收器和文件。外部 HTTP 没有条件提交时，仍只封存为 `OUTCOME_UNKNOWN`，不自动再执行。
