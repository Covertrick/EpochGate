# EpochGate: An Empirical Study of Revocation, Effect Recovery, and Execution Overhead in Tool-Using Agent Runtimes

工具型 Agent Runtime 中资格撤销、副作用恢复与执行开销的实证研究。

状态：草稿。数字冻结在 2026-11-10 的 `数据/tables.json`。没有投稿。

## 摘要

一个原来合法的工具动作，执行期间可能失去资格。EpochGate 把提交放在 fencing token、Run 版本和 EffectSink 版本同时匹配的时候。本文测量三件事。外部状态变了但没有通知时，旧 token 仍会写入。对齐通知之后，旧 token 被拒绝，新 token 可以完成。只推进 Run、不推进 sink 时，新 token 也会被拒绝，合法后继停住。四个崩溃点各重复 3 次，sink 接受次数是 0、0、1、1。公平开销实验里，三臂都完成同一次 `OK` 提交：B0、B1、B2 的总时间中位是 0.878 秒、1.034 秒、1.067 秒（各 20 次）。多出来的时间主要在提交段，不在模型段。本文不提出新算法，也不报告 SWE-bench 修复率。

## 1. 问题

工具调用开始之后，库存、文件或授权仍可能变化。调用方当时拿到的依据会过期。把「取消请求已发出」「进程已退出」「资格仍有效」和「效果已落地」收成一个布尔值，会把这几件不同的事混在一起。

旧工作给出了这个问题的不同切片。4.0 在逻辑时钟上看到失效工作传到旁观者等待。5.0 说明客户端可见的停止不能证明后端已经释放。UCR-2.1 没有证明未验证的停止预测更好。RRM-1 能审计取消路径，但不能把审计写成资源回收。这些结果留在档案里，不和本文的样本相加。

本文问的是当前这套 RunLedger：资格失效时它挡住了什么，放行了什么，崩溃后能对上什么，以及这些检查要付多少时间。

## 2. 保证

一次提交要同时满足：

1. fencing token 等于 Run 的当前 token。
2. 调用方的 `state_version` 等于 Run 的当前版本。
3. EffectSink 的版本等于这个 `state_version`。

`supersede(run, sink)` 把三者一起推进。`supersede(run)` 只推进 Run。`revoke` 取消资格，不留下后继。幂等键完成后再次提交返回原来的 receipt，sink 不增加接受次数。效果处于 `started` 或外部系统不能条件提交时，结果是 `UNKNOWN`，不自动再执行。

这些是本系统的检查规则，不是新的授权理论。

## 3. 实现

DSH 负责模型和会话。`eg-workspace` 在有控制地址时把每次工具调用送到 RunLedger。`eg_read` 只做准入。`eg_write` 先 `reserve`，再把暂存文件交给 `publish-file`。`claim_publish` 在发布时核对 fencing token。这条文件路径不读取 EffectSink 的版本。

2026-11-10 补了两条多步会话，模型是 `deepseek-flash`。任务是读 `stock.txt`，再写 `order.txt`。`EG_PUBLISH_GATE` 让第一次 `eg_write` 停在 reserve 之后、publish 之前，控制服务把库存从 3 改成 0。这是受控停顿，用来把通知放进一次工具调用内部。模型自己不会调用 `supersede`。

| 会话 | Run | 模型调用 | 账本事件 | 文件 |
| --- | --- | --- | --- | --- |
| 没有通知 | `dsh-452adcb9b31e` | `eg_read`，`eg_write` | `intent_recorded`，`file_published` | 库存已是 0，`order.txt` 仍是 `order 3`，token 保持 1 |
| 对齐通知 | `dsh-963323c7fb0c` | `eg_read`，`eg_write`，`eg_read`，`eg_write` | `intent_recorded`，`eligibility_superseded`，`result_withheld`，`intent_recorded`，`file_published` | token 1 的效果停在 `INTENT_RECORDED`；token 2 发布 `order 0` |

对齐通知是 `POST /runs/{id}/supersede`。响应里 token 和 `state_version` 都是 2，Run 仍可继续。模型没有收到额外的追问，自己读了新库存并完成第二次写入。原始记录在 [数据/01-主实验/dsh_revocation.json](数据/01-主实验/dsh_revocation.json)。

先前那次单步发布仍在：Run `dsh-0dd9ee3abc53` 写了 `note.txt`。直接调用 `commit_authorized` 的三例仍用来说明 sink 版本，不并进这两条 DSH 轨迹。

## 5. 撤销和后继

每个确定性场景重复 5 次，5 次都与预期相同。模型三例各 1 次，模型都按要求回复，每次 25 token。

| 场景 | 结果 | 旧动作被挡住 | 新动作完成 |
| --- | --- | --- | --- |
| 没有通知 | 旧 token 写入 `reserve:1` 或 `COMMIT reserve:3` | 否 | 不适用 |
| 通知晚于提交 | 已经接受的效果还在 | 否 | 不适用 |
| 对齐的 `supersede(run, sink)` | 旧 token 拒绝，新 token 完成 | 是 | 是 |
| 重复对齐通知 | 最后一对 token 和版本可以提交 | 是 | 是 |
| 只调用 `supersede(run)` | 旧 token 和新 token 都拒绝 | 是 | 否 |
| `revoke` 之后再提交 | 拒绝，接受次数 0 | 是 | 否 |
| 先提交再 `revoke` | 第一次完成，下一次拒绝，receipt 仍在 | 是 | 否 |

模型在对齐条件下回复 `COMMIT reserve:0`。旧 token 被拒绝，新 token 完成。在未对齐条件下，模型回复同样的句子，但两次提交都是 `rejected`，sink 接受次数是 0。

这组结果里有三条可以直接写进正文的观察。

第一，撤销依赖通知。库存从 3 变成 0，只要没有 `supersede`，旧 token 仍然有效。

第二，安全和不中断不是同一件事。对齐通知同时给出「旧的被拒绝」和「新的能完成」。未对齐的 `supersede` 挡住了旧动作，也挡住了合法后继。按第 2 节的规则，后者是版本没有一起推进，不是预期的安全拒绝。

第三，已经落地的效果不会被事后的撤销抹掉。

## 6. 故障恢复

四个崩溃点各跑 3 次，worker 退出码都是 86。

| 崩溃点 | 对账 | sink 接受次数 |
| --- | --- | --- |
| 派发前 | `not_applied` | 0 |
| 写入 sink 前 | `not_applied` | 0 |
| 写入 sink 后、receipt 前 | `confirmed_from_sink` | 1 |
| receipt 已写入 | `replay` | 1 |

同一幂等键的第二次提交是 `replayed`，接受次数保持 1。`started` 未确认时提交结果是 `unknown`，接受次数 0。外部不可确认效果第二次是 `replayed`，`retry` 为 false。

8 次真实短进程取消都退出并释放槽位。取消到退出的 8 个秒数是 0.712、0.929 附近到 1.084，最小 0.712，最大 1.084。原文在 `tables.json` 的 `cancel_seconds`。

撤销和提交的并发做了 20 次。20 次都是提交先完成，状态 `completed`，sink 接受 1 次，和账本一致。这 20 次没有观察到撤销先赢。不能把这个样本写成两种交错的比例。

| 臂 | 总时间中位 | 最小–最大 | 提交段中位 | 重开账本中位 |
| --- | --- | --- | --- | --- |
| B0 sink 版本检查 | 0.878 秒 | 0.443–1.521 | 0.096 秒 | 0 |
| B1 `commit_authorized` | 1.034 秒 | 0.682–1.668 | 0.283 秒 | 约 0 |

## 8. 可以从测量里带走的句子

没有通知，过期依据就会提交。通知若不同时推进 sink 版本，新动作也会停住。崩溃点不同，sink 里的行可能是 0 或 1，恢复结论不能只看进程退出码。账本提交相对一次短模型调用，中位大约多 0.2 秒的提交段。这些都是这套实现上的测量，不是普遍定律。

## 9. 限制

DSH 的撤销发生在受控停顿里，不是模型自己发起的。`eg_write` 的发布检查的是 fencing token，不是 EffectSink 版本。10 个确定性场景不是一份大矩阵。竞争实验没有覆盖撤销先赢的交错。开销只在并发 1 的短调用上。12907 的两个官方节点能分开基线和 gold patch，没有 Agent 补丁，不能写成修复率。4.0、5.0、UCR、RRM 和 M0-R 的数字不并进本文样本。

## 10. 结论

在这套 RunLedger 上，对齐的资格通知可以拒绝旧提交并完成新提交。缺通知或版本没有一起推进时，这个结果不成立。四个崩溃窗口的 sink 接受次数可以复核。公平对照下，持久提交的额外时间主要出现在提交段。稿件到这里可以继续写，还不能投稿。
