# v5.1 机制

脚本校准和本机 vLLM 分开记。脚本里的 0.05 秒是注入的，不是这次引擎上看到的取消。

## 本机 vLLM

2026-11-04 在 RTX 4060 8GB 上用 Windows 轮子 vLLM 0.32.0 跑了四组各一次。模型 `Qwen/Qwen2.5-1.5B-Instruct`，fp16，Triton attention，eager。细节和改读后的表在 [v5.1-vLLM四组.md](./v5.1-vLLM四组.md)，原始事件在 `results/experiments/v5_1/vllm/groups.json`。

更早的 `results/experiments/v5_1/vllm/compat.json` 是服务还没起来时的探测，`reachable=false`。它不被这四组覆盖，也不再代表最终状态。

能写下来的只有这些：

- G2-hold-slot 比 G2-local 晚 1.516 秒把本地槽交给 bystander-0，和握槽的 1.5 秒一致。
- 这 1.5 秒里 `vllm:num_requests_running` 已经是 0。下一条请求进入之后，计数才回到 1。
- `finished_reason=abort` 四组前后都是 0。断流的那条也没有计入 `stop`。看到的是请求离开 running 集合，没有 abort 回执。不能写成 L2-a。
- 这次采样没有记下 KV。指标名在这一版是 `vllm:kv_cache_usage_perc`，脚本找的是旧名。L2-c 不可观测。
- G0 的 11 秒含首请求预热，不拿来和后三组比效应量。

这组对照说明：在这台引擎上，本地槽可以在 running 已经为 0 时继续挡住下一条独立请求。它没有给出可重复的、M0 解释不了的后端残余。

## 脚本四臂

种子 9100。KV/GPU 不可观测。`abort_confirmed` 只表示本地停读，`provider_abort_ack=false`。

- G0: slot_released=0.0001s left_scheduler_queue=0.0001s
- G2-local: slot_released=0.0000s left_scheduler_queue=0.0000s
- G2-residual: slot_released=0.0000s left_scheduler_queue=0.0657s
- G2-hold-slot: slot_released=0.0630s left_scheduler_queue=0.0001s

G2-residual 的 `left_scheduler_queue` 晚于放槽，因为残余是 `injected-script`。G2-hold-slot 的放槽晚于离开脚本队列。这两组只说明仪器能把三种事件分开记。
