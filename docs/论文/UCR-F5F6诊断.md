# UCR F5/F6 诊断

日期：2026-11-06。数字由 `scripts/diagnose_ucr.py` 按冻结生成器重算，写在 `results/experiments/ucr/diagnosis.json`。这篇不改结论，只判断失败来自实现还是来自研究假设。

## 判断

F5 和 F6 的覆盖失败是外推失败，不是“生成器不可预测”，也不是特征没接上。

剩余服务在生成器里近似只由参数字段数决定：

\[
S \approx 6\times(0.55\times\text{fields}+1.4)
\]

token 速率在分子和分母里约掉，`generated_tokens` 不进入这个公式。开发集字段数只有 1–5，对应 \(S\) 大约 10.6–24.9 秒。F5 的字段数是 12–20，100 条都落在训练支持域外面，真实 \(S\) 是 47.0–74.4 秒。深度为 2 的梯度提升树不会沿这条直线外推，预测停在训练叶子附近。F5 上 \(S\) 的原始非一致性分数最小已经是 22.2 秒，大于校准给出的扩张 13.2 秒，所以扩张之后覆盖率仍是 0。

F6 的字段数仍在 3–5，\(S\) 覆盖率是 1。它的重规划尺度是 2.5，训练只见过 0.6 和 1.0。真实 \(C\) 的中位数是 50.6 秒、最大 133.2 秒。`recent_restart_service` 这个特征是接上的，但 95/100 条超出训练最大值 2.20，树同样截断。100 条里有 20 条 \(C\) 落在区间外，覆盖率 0.80。

研究假设“浅层分位数树加 CQR，能覆盖没见过的字段长度和重规划尺度”在这个生成器上不成立。换成能外推字段数的线性分位数模型，F5 的 \(S\) 是有机会被预测的。这不是世界本身没有规律。

另外有两处实现没有把协议里的结构变化接到标签上。`timing` 在八个族里都写了，生成器没有读它。工具类型不进入 \(S\) 或 \(C\)。所以 F7、F8 的覆盖率看起来正常，不能当成“留出工具和谓词时刻已经通过”。

## 覆盖失败落在哪里

F5 的 100 条全部失败，工具都是 reserve（编码 0），谓词 valid / invalid / changed 各约三分之一，字段数 12–20。失败不挑谓词，只挑字段长度。

F6 失败 20 条，工具仍是 reserve，三种谓词都有（7、7、6），字段数 3–5，都在训练范围内。失败的是 \(C\)，对应重规划尺度 2.5，不是字段长度。

F3 作为校准集自己就有 67/200 条在原始区间外，字段 6–10。用一个已经整体上移的校准集去扩张，不能保证更远的 F5。

## 宽度为什么不随已生成 token 下降

F5 上 `generated_tokens` 和真实 \(S\) 的相关系数是 −0.018，和区间宽度的相关系数是 −0.069。token 不大于 20 与大于 20 的平均宽度都是 34.2 秒。开发集上也是这样：F1 的两组宽度是 31.19 和 31.23。

原因在生成器。`tokens_left` 乘了真实速率，\(S\) 再除以同一个速率，速率约掉。已生成 token 是 4 到 48 的独立均匀整数。模型即使把这个特征放进 \(f_S\)，也看不到“生成越多、剩余越短”。宽度主要由那一次 13.2 秒的全局扩张决定，所以它几乎是常数。

## 和 Gate 的关系

Gate A 失败，是因为 F5 的字段外推和 F6 的尺度外推没有被浅层树和一次全局扩张盖住，再加上宽度不被 token 驱动。Gate B 和 probe 消融失败，是因为区间宽到大约 31 秒，几乎总是重叠，而校准集上的信息价值没有超过 probe 代价，Full 和 Point 走了同一个保守继续。Gate C 的安全记录不受这个生成器影响。Gate D 因此不通过。

结论保持为：安全闭环成立，非 Oracle 策略收益未证明。若要再试，应先让剩余服务真正依赖已生成 token，并让谓词时刻和工具类型进入 \(S\) 或 \(C\)；在那之前，换模型也只是在一条过短的直线上做外推。
