# EpochGate 论文初稿

骨架只标出要写的论点和已经落地的机制。没有填吞吐、延迟或名次。这些数字要等冻结配置上的实测，不能用假后端的成功数代替。

## 引言

多个工具智能体共享有限的推理槽，外部状态在排队和生成期间继续变化。计算完成不等于任务成功：动作必须在截止时间前、带着仍然有效的观测被环境接受。

EpochGate 是这一层的运行时。它把观察、准入、派发和取消分开，并用版本把「可以执行」和「结果仍然有效」拆开。本文比较的是同一环境、同一到达、同一槽位上的调度策略，而不是更换模型。

## 相关工作

- Concord：把一致性放在共享状态的提交条件上。EpochGate 保留条件提交，另外决定何时重查、谁先占用推理槽。
- ATR：关注推理期间任务是否还值得继续。EpochGate 用前提检查和取消分级表达这件事，并且不把非流式 HTTP 的取消回执写成 GPU 已经停止。
- ERRAND：讨论过期结果的代价。EpochGate 把过时动作分成候选过时、网关拦截、提供者拒绝和检查窗口内的过时提交，分开计数。

这三份工作都还没有在本文里复现。相关工作只说明差异，不引用未经核对的榜单。

## 设计

运行时循环是：拉取变化、丢弃过期租约、探测在途前提、让调度器只读快照、再执行刷新、准入、派发或取消。只有网关调用 `commit`。

策略：

- B0 入队观察一次，按到达顺序派发，忽略之后的变化。
- B1 只在没有观测时观察一次，按最早截止派发。
- B2 在派发前再查一次，不因变化取消。
- B3 在版本差、预算和最小间隔下刷新，刷新当拍不发租约。
- J0 与 B3 使用同一门闩，但可以在刷新当拍发租约。风险打分关闭。
- J1 在 J0 的准入上计算 `U = P_finish * P_available / (C_model + kappa * C_observe + epsilon)`。`execute`、`refresh`、`wait` 三者里 `wait` 的效用是 0。
- `event` 只在缺观测或版本差时刷新，用来对照 B2 的固定重查。

B3、J0、J1 用 `deadline - weight * waited` 排序。每 N 次派发留一个槽给等待最久的可执行任务；等待相同时长任务（`loose`）优先。

变化通知和模型 HTTP 故障分开。断流把依赖标成未知，调度退回保守重查。

## 局限

- 非流式接口不能观察服务端是否停止了计算。资源回收不可观测。本轮没有接 vLLM 或 SGLang，论文不得把取消确认写成显存已经释放。
- SQLite 库存是单机 WAL。8 个进程各写 25 行的测试只说明没有丢行、没有重复行，不是分布式事务。
- Gaia2 的动作粒度不是 `observe` / `commit`。RealtimeGym 用时间或 token 预算推进。两边都没有接入，因此没有跨环境名次。原因见 [第二环境.md](./第二环境.md)。
- 假后端不产生 `usage_source=backend` 的 token。浪费 token 在这些 trace 上是 0。
- 同一任务因版本冲突重开的次数有上限。这是为了让忽略 dirty 的 B0 能够结束，不是调度策略本身的决策。
