# EpochGate 论文初稿（v1.2 实证收敛版）

本文基于 EpochGate `v1.2.0` 的冻结协议与真实流式 API（`deepseek-chat`）配对实验结果撰写。所有主结论严格区分**客户端可观察输出（H1）**、**Runtime 本地执行槽位占用（H2）**、**串行队列等待与恢复净收益（H3）**以及**外部副作用安全不变量（H4）**，不将客户端 HTTP 断流夸大为服务端 GPU 算力或计费节省。

## 1. 引言与核心研究问题

当依赖外部易变状态的 LLM 工具调用智能体（Tool-Using Agent）在流式生成期间遭遇外部状态变化、使当前在途尝试（Attempt）失去执行资格时，Agent Runtime 面临两个层面的问题：
1. **外部副作用安全性**：过时或前提已失效的候选动作绝不能被提交执行；
2. **本地执行槽位与队列效率**：若只在线性化点撤销旧 attempt 的提交资格、但任由旧流式请求继续读取完毕（Arm A），旧流将持续占用 Runtime 有限的本地执行槽位，造成后续有效任务或重规划任务的队头阻塞（Head-of-Line Blocking）。

**本文主假设**：当一个 Agent attempt 因外部状态变化失去执行资格时，在线性化撤销资格的同时立即中止其本地流式读取（Arm B），相比继续读取并在 Gateway 拒绝旧结果（Arm A），能够缩短失效 attempt 对 Runtime 本地执行槽位的占用，并在任务剩余生成时间大于变化窗口及存在串行队列竞争时，显著改善后续有效任务的排队等待和恢复时间，同时严格保持外部副作用零违规。

## 2. 相关工作与创新性边界审查

除早期事务一致性与过时结果工作（Concord、ATR、ERRAND）外，我们将 EpochGate 与最新的 5 类相关工作按 **7 个维度** 严格对比：

| 工作 / 方向 | 研究对象 | 停止/触发条件 | 取消粒度 | 取消后任务是否继续 | 资源指标 | 外部副作用正确性约束 | 队列与多任务槽位指标 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **AgentStop** | 消费级终端本地 Agent | 预测任务失败或陷入死循环（内生特征） | **Task 级** 终止 | **否**（放弃任务省电） | 终端能耗 (J) | 无外部状态版本门闩 | 无多任务槽位排队指标 |
| **Runaway is Ashamed, But Helpful** | 具身环境 LLM Agent | 模型自身判断受阻主动 early-exit | **步级 / 轨迹级** 自我退出 | 退出或求助，非版本驱动重规划 | 交互步数、轨迹 token | 无多会话 CAS 门闩 | 无 Runtime 槽位竞争度量 |
| **When Agent Context Goes Stale** | 易变上下文下的 Agent 推理 | 外部数据变化导致上下文陈旧 | **上下文诊断与刷新**（无在途断流） | 刷新重试 | 不一致率、准确率 | 分析陈旧危害，未结合流式取消释放槽位 | 无槽位与队列传递效应 |
| **Stale Does Not Mean Unsafe** | 基础设施竞态下的工具守卫 | 提交前检查状态变化是否破坏前提 (`premise_holds`) | **提交点门闩验证** | 前提破坏则拒绝并重规划 | 误拒率、通过率 | **高**（精确前提守卫） | 聚焦提交点守卫精度，未量化**在途流式断流对本地槽位与排队短任务等待的改善** |
| **LLM Serving Cancellation / Preemption** (vLLM, SGLang, Orca) | 自托管 GPU 推理引擎 | 客户端断连或高优抢占 | **服务端解码迭代级** | 服务端不管 Agent 重观察重规划 | 服务端 KV 显存、GPU 算力 | 无业务层副作用与观测版本概念 | 服务端 batch 吞吐，不涉及客户端 Runtime 队头阻塞 |
| **EpochGate (v1.2)** | **黑盒流式 API 之上的多任务 Agent Runtime** | **外生状态变化 + 前提探测失败 (`dirty & !premise_holds`)** | **在途 Attempt 级本地流中止 (`local_read_abort`)** | **是**（释放槽位并按 FIFO 入队尾重观察、重规划） | **客户端可观察失效词元 (`tiktoken`) + 本地槽位持有时间 (`slot_hold_s`)** | **严格零违规**（Gateway 锁内线性化撤销 + 版本条件提交） | **串行槽位队头阻塞消除、后续任务等待分布 (Median/P90/P95) 与客观饥饿计数** |

**创新性边界声明**：本文不将普通 HTTP `aclose()`、通用 Agent Early Exit、单纯的提交前版本门闩或上下文刷新作为独立创新主张；本文的核心贡献在于**揭示并实证量化了“外部状态失效触发的在途 attempt 级流式取消”对 Agent Runtime 本地执行槽位释放、后续排队任务队头阻塞消除以及恢复净收益的系统效应与适用边界**。

## 3. 系统设计与六维取消能力合同

1. **双层保护与唯一处理变量**：Runtime 在感知外部来源变脏且前提探测失败（`premise_holds == False`）时，先在 Gateway 准入锁内执行 `linearize_revoke`（发出 `eligibility_revoked`），再向后端发出 `cancel_requested`。Arm A（`stop_on_cancel=False`）与 Arm B（`stop_on_cancel=True`）共享完全相同的资格撤销门闩、初始观测、独立定时 `ScenarioDriver` 与 `FifoAdmissionScheduler(replan_to_tail=True)` 队尾重规划规则，唯一处理变量是**资格撤销后是否中断客户端本地流读取**。
2. **取消能力合同（F3）**：`local_read_abort` 与 `client_stream_close_issued` 表示客户端停止读取。`provider_cancel_api_invoked` 与 `provider_cancel_ack_received` 在当前商业流式后端上为假，确认语义记为 `UNKNOWN`。`response.aclose()` 不是供应商取消 API。即使后端不支持取消或为非流式接口（`HttpToolBackend`），Gateway 资格门闩依然拦截过时提交。

## 4. 实验评测（阶段 E 与阶段 F 确认性结果）

完整实验数据与复算脚本见 [阶段E独立复核.md](./测试记录/阶段E独立复核.md) 与 [阶段F实验协议与结果.md](./测试记录/阶段F实验协议与结果.md)。

### 4.1 安全性不变量 vs 任务可用性（H4）

- **安全性不变量（零容忍）**：在阶段 E（64 行）与阶段 F 确认性测试集（120 行）共 **184 条真实 API 测试任务行**（以及全部离线确定性剧本）中，被撤销旧 attempt 提交次数 **`old_attempt_committed = 0`**，重复副作用次数 **`0`**，Gateway 精确拦截并记录了 **134 次**过时/库存不足候选动作。
- **队列任务可用性**：在 F4 的 6 个确认性多任务队列批次（每臂 20 个任务）中，Arm B 完成 **`20/20 (100%)`** 有效提交且 **0 次饥饿**；Arm A 完成 `19/20 (95%)` 且在 4 任务混排中发生 **2 次**预设客观饥饿事件。

### 4.3 观察成本隔离（F2 `refresh_only`）与 FIFO 串行队列效应（F4 / H3）

- **观察成本隔离（F2）**：通过 `observe_delay_scope="refresh_only"` 将额外观察延迟（`0.0s / 0.5s / 2.0s`）严格限制在状态变脏后的重观察阶段（初始观察中位耗时恒为 `0.00018s`）。在 `long_early` 下，即便重观察延迟达 `2.0s`，B 臂节省的约 `3.83–4.32s` 本地槽位仍带来 **+1.28 s 至 +2.73 s** 的正恢复净收益（\(\Delta T_{\text{recovery}}\)）。
- **串行队列队头阻塞消除（F4）**：在 `max_inflight=1` 与严格 `FifoAdmissionScheduler(replan_to_tail=True)` 下，跨平稳混合（`F4a`）、突发到达（`F4b`）与 4 任务混排（`F4c`）共 6 个确认性批次，B 臂使后续排队任务首次等待时间 **6/6 批次全部下降**，批次聚类均值缩减 **2.49 s**（95% CI **[1.26, 3.72] s**），后续任务等待中位数从 **6.92 s** 降至 **4.49 s**（P95 从 **12.11 s** 降至 **10.23 s**）。

## 5. 局限性

1. **服务端资源与计费不可观测**：商业流式 API 在客户端 `aclose()` 后不返回 usage chunk。`aclose()` 只证明本地停止读取。服务端何时停止解码、是否收到取消确认、是否释放 KV 缓存，都不可观测（记为 `UNKNOWN`）。本文不声称节省服务端 GPU 或账单费用。
2. **串行槽位负载范围**：阶段 E3 与 F4 度量的是 `max_inflight=1` 下的串行执行槽位队列压力与队头阻塞，不能直接外推为多连接高并发（`max_inflight > 1`）服务端吞吐结论。
3. **重规划轮的模型工具调用方差**：真实 LLM 在重规划轮偶发出现只输出解释文本而未调用 `reserve` 工具（`model_no_action`）以及生成长度波动，在短任务上会掩盖小于 1 秒的槽位释放收益。
