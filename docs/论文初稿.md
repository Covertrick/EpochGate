# EpochGate v1.2 实证记录

这是 **v1.2.0** 的真实流式 API 证据，模型是 `deepseek-chat`。它回答的是：资格撤销之后，立刻停止本地读取，会不会少占 Runtime 槽，并缩短后面任务的第一次等待。

它不是 4.0 的旁观者论文。这里的“后续任务等待”没有 `workflow_role`，不能改名为旁观者 P95。旁观者测量见 [论文4.0.md](./论文4.0.md)。原始复核在 [测试记录/阶段E独立复核.md](./测试记录/阶段E独立复核.md) 和 [测试记录/阶段F实验协议与结果.md](./测试记录/阶段F实验协议与结果.md)。

## 面试时先说的三句

1. Gateway 在锁内撤销资格。过期 attempt 的提交次数是 0，重复副作用是 0。
2. Arm B 相对 Arm A，在三个主单元上少看到约 465 词元失效文本，少占约 3.70 秒本地槽。
3. `response.aclose()` 只停止客户端读取。服务端是否还在算、是否释放 KV，记为 `UNKNOWN`。

## 1. 问题

外部状态在流式生成中途变化，当前 attempt 失去执行资格。运行时要同时守住两件事：

| 层 | 要求 | 失败会长什么样 |
| --- | --- | --- |
| 资格 | 过期动作不能提交 | 旧 attempt 仍然 `commit` |
| 槽位 | 失去资格之后不必把流读完 | 队头一直占着唯一的槽 |

**假设。** 在同一套资格门闩、同一份外生时间表、同一种 FIFO 队尾重规划下，唯一处理变量是撤销之后停不停本地读。Arm B（`stop_on_cancel=True`）相对 Arm A（继续读到网关拒绝）应缩短失效占用，并在串行队列上缩短后续任务的首次等待，同时旧提交保持为 0。

## 2. 系统和唯一处理变量

来源变脏且 `premise_holds == False` 时，Runtime 先在 Gateway 锁内 `linearize_revoke`，再向后端发取消。Arm A 与 Arm B 共享门闩、初始观测、`ScenarioDriver` 和 `FifoAdmissionScheduler(replan_to_tail=True)`。

取消合同把四件事分开：

| 字段 | 本实验里表示什么 |
| --- | --- |
| `local_read_abort` / `client_stream_close_issued` | 客户端停止读取 |
| `provider_cancel_api_invoked` | 是否调用了供应商取消接口。商业流式后端上为假 |
| `provider_cancel_ack_received` | 供应商是否确认。没有这条回执 |
| Gateway 拒绝 | 即使后端不能取消，过期提交仍然被拦住 |

## 3. 和邻近工作差在哪

下表是 v1.2 当时的边界，不是 4.0 的文献复核。4.0 核对过的论文在 [论文4.0.md](./论文4.0.md) 第 2 节。

| 工作 | 它停的是什么 | 它没有测的 |
| --- | --- | --- |
| AgentStop | 预测失败后终止整个任务 | 外部状态版本门闩，多任务槽位 |
| Runaway is Ashamed, But Helpful | 模型自己提前退出 | Runtime 槽位竞争 |
| When Agent Context Goes Stale | 刷新陈旧上下文 | 在途断流 |
| Stale Does Not Mean Unsafe | 提交前检查前提 | 断流对后续等待的影响 |
| vLLM / SGLang / Orca | 服务端解码级抢占 | 客户端 Runtime 的队头阻塞 |
| EpochGate v1.2 | 外生变化且前提失败时，停本地读，任务可以重规划 | 服务端 GPU 和账单 |

不把普通 `aclose()`、通用提前退出或单独的提交前门闩写成创新。v1.2 量化的是：在途停读对本地槽位和后续任务首次等待的效应，以及它在短任务、晚时机上消失的边界。

## 4. 结果

阶段 E 64 行加阶段 F 确认性 120 行，共 184 条真实 API 任务行。离线剧本另计，不混进下面的秒数。

### 4.1 旧提交

184 条里 `old_attempt_committed = 0`，重复副作用为 0。Gateway 记下 134 次过时或库存不足的拒绝。

F4 的 6 个确认性队列批次、每臂 20 个任务：Arm B 有效提交 20/20，饥饿 0 次。Arm A 是 19/20，4 任务混排里有 2 次预先定义的饥饿。

### 4.2 失效文本和本地槽位

三个主单元上，双臂都触发的 5 个配对等权：失效文本均值 **465.2** 词元，区间 **[334.4, 567.8]**；槽位均值 **3.70** 秒，区间 **[2.63, 4.55]**。区间是这 5 个配对差的重采样，不是 Holm 检验。三个单元再等权是 425.2 词元和 3.38 秒。口径复核见 [测试记录/v1.3-证据闭环.md](./测试记录/v1.3-证据闭环.md)。

| 单元 | 角色 | 触发率 | 文本差（词元） | 槽位差（秒） |
| --- | --- | ---: | ---: | ---: |
| `F1M_long_early`，450 词，0.25 秒 | 主确认 | 1.00 | +552.0 | +4.70 |
| `F1M_long_mid`，450 词，0.80 秒 | 主确认 | 1.00 | +498.5 | +3.66 |
| `F1M_mid_mid`，200 词，0.80 秒 | 主确认 | 0.75 | +225.0（n=1） | +1.77（n=1） |
| `F1M_long_late`，450 词，1.80 秒 | 边界 | 1.00 | +322.0 | +2.24 |
| `F1M_short_early`，50 词，0.25 秒 | 边界 | 0.50 | +61.0 | +0.87 |
| `F1M_short_mid`，50 词，0.80 秒 | 边界 | 0.25 | 对不齐 | 对不齐 |
| `F1M_short_late`，50 词，1.80 秒 | 边界 | 0.00 | 对不齐 | 对不齐 |

短任务、晚时机经常来不及触发。收益随“变化早、生成长”变大，不是一条常数。

### 4.3 队列

`max_inflight=1`，FIFO 队尾重规划。平稳、突发、4 任务混排共 6 个批次：Arm B 的后续任务首次等待 **6/6** 下降。批次聚类均值少 **2.49** 秒，区间 **[1.26, 3.72]**。中位数从 **6.92** 秒降到 **4.49** 秒，P95 从 **12.11** 秒降到 **10.23** 秒。

这是串行槽上的后续任务首次等待。4.0 才把旁观者、后继和误撤目标分开。

F2 把额外观察延迟只加在变脏之后的重观察上。`long_early`、重观察延迟 2.0 秒时，B 臂仍有大约 1.3 到 2.7 秒的正恢复净收益。细节在阶段 F 记录，不在这里再列一张表。

## 5. 不能外推的三件事

1. 商业 API 在 `aclose()` 之后不返回 usage。服务端解码、取消确认、KV，都是 `UNKNOWN`。不写 GPU 或账单节省。
2. F4 是 `max_inflight=1`。不能写成多连接吞吐。
3. 重规划轮里模型有时不调用工具。短任务上，小于 1 秒的槽位差会被这种方差盖住。
