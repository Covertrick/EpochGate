# 开发中遇到的问题

从 v0.2 做到 3.0.0，实际撞上并处理过的问题。取消回执仍然不能当成 GPU 已释放，这是语义缺口，不是已经修好的缺陷。第二套公开环境没有接上，原因在 [../第二环境.md](../第二环境.md)，这里不写跨环境名次。v1.3 到 v2.0 的口径问题补在最后两节，不回改当时的 JSONL。

## 环境

### PowerShell 不能用 `&&`

现象：把两条命令用 `&&` 串起来时，PowerShell 直接语法错误。

原因：这台机器的 PowerShell 不支持 bash 的 `&&`。

处理：改成 `命令; if ($LASTEXITCODE -eq 0) { 下一条 }`。

### 系统 Python 是 3.10，`uv` 不在 PATH

现象：直接跑 `uv` 找不到命令。仓库要求 Python 3.12+。

原因：默认 `python` 是 3.10。`uv` 装在用户目录，没有进 PATH。

处理：用 `python -m uv`。测试和联调实际跑在 uv 管理的 CPython 3.15.2 上。

### PyYAML 在 3.15 上编不过

现象：把 PyYAML 加进依赖后，`uv lock` 要编译 6.0.3，报缺少 Microsoft Visual C++ 14.0。这一版没有 cp315 的轮子。

原因：场景文件只需要很少的 YAML，不值得为它装编译器。

处理：从 `pyproject.toml` 和 `uv.lock` 去掉 PyYAML。`faults.py` 自己解析本仓库用到的子集：标量、故障列表、`modes` 列表。

## v0.2

### 外生变化把刷新预算耗尽

现象：stale commit 的测试里，任务一直刷新，最后停住，该成功的提交没有发生。

原因：每次 `submit` 都在 `on_start` 里再改一次库存。世界被自己的测试钩子不停打脏。

处理：外生变化只触发一次。

### 访问 127.0.0.1 得到 HTTP 502

现象：本机假的 chat completions 服务是通的，httpx 却返回 502。

原因：`trust_env=True` 时 httpx 走了系统代理，代理不接受回环地址。

处理：打本机服务时 `trust_env=False`。打 DeepSeek 时保持 `trust_env=True`，否则真实请求过不了代理。库存服务同样用 `trust_env=False`。

## v0.3

### 库存还够时也被取消

现象：观测变脏、但库存仍然满足时，临近准入发出了取消。

原因：规则策略把「变脏」直接当成要取消。临近准入应该先向环境 `check`。前提仍成立就不能取消。

处理：只有 `premise_holds is False` 且环境声明支持取消时才取消。库存还够的用例不断言取消；库存从 1 被外生改成不够的用例才断言取消、迟到结果被拒绝，证据里不出现 gpu。

### B2 的重查次数和原因对不上

现象：对照实验里，B2 要么给每个 READY 任务都重查一次，要么 trace 里看不到 “recheck before dispatch”。

原因：有两个独立问题。空闲槽在发重查时没有扣掉，同一轮里每个准备好的任务都重查了。刷新事件的原因只写了 `n=1`，决策理由没有带上。

处理：发出派发前重查时先占用一个槽，这样一轮只重查即将派发的那一个。`observations_refreshed` 的原因写成 `n=<数量>; <决策原因>`。测试要求 t0 的刷新次数比 B0 恰好多 1。

## v0.4

### 故障断言被空格绊倒

现象：概率为 1 的故障测试失败，trace 里其实已经有故障。

原因：断言找的是 `"fault_injected": true`。写出的 JSON 是紧凑的 `"fault_injected":true`。

处理：两种写法都接受。

### 密钥不该进用户环境，也不该进仓库

现象：需要 DeepSeek 才能做真实冒烟，但不能 `setx`，也不能把密钥写进代码、文档、锁文件或 manifest。

原因：用户环境是长期的。manifest 和结果目录会进版本库。

处理：密钥只放在仓库根 `.env`。`.gitignore` 忽略 `.env`。命令启动时只把尚未设置的变量填进当前进程。manifest 只记 `EPOCHGATE_BASE_URL`、`EPOCHGATE_API_KEY`、`EPOCHGATE_MODEL` 是 set 还是 unset。

### `.env` 让「未配置就退出」的测试失效

现象：测试删掉三个环境变量后，`http-smoke` 仍然能读到配置，退出码不是 2。

原因：`http_settings()` 会再读 `.env`，把刚删掉的变量填回来。

处理：这个测试把 `load_project_env` 换成空操作，只验证「进程里没有这三个变量时退出」。

### 冒烟直接调用了 `environment.commit`

现象：架构测试要求除 `gateway.py` 外不能出现 `env.commit`。新的冒烟清单被扫出来。

原因：ASGI 检查为了省事走了 `HttpInventoryEnvironment.commit`。那条规则要保证的是运行时只有网关能提交。

处理：冒烟改成用 httpx 直接 `POST /observe` 和 `POST /commit`。这样测的是 HTTP 面，也不破坏「只有网关提交」。

### `env-serve` 打不开数据库

现象：`epochgate env-serve --db traces/inventory.sqlite` 抛出 `OperationalError: unable to open database file`。

原因：`traces/` 还不存在。SQLite 不会替你创建上级目录。`traces/` 是本地输出，被 gitignore，仓库里本来就没有这个目录。

处理：启动前创建 `traces/`。

### 用户给的冒烟命令会打错服务

现象：建议的命令是 `EPGATE_API_KEY`，并且 `http-smoke --base-url http://localhost:8080`。库存服务也开在这个端口。

原因：项目里的变量名是 `EPOCHGATE_*`。`--base-url` 是模型的 chat completions 地址。把模型请求打到库存端口上，对不上 API。

处理：模型地址用 `.env` 或 `--base-url`。库存地址用 `--env-url`。不传 `--env-url` 时用 ASGI，不监听端口。

### 故障条数用计划代替了 trace

现象：只要 `FaultPlan.fired` 里有记录，cell 就会被判成有效，哪怕 trace 没写上 `fault_injected`。

原因：有效性用的是计划掷出的次数，不是日志里的事件数。正概率但零记录时，这个 cell 不能当成「没有故障」。

处理：`cell_valid` 改为数 trace 里的 `fault_injected`。条数和 `fired` 不一致就标无效，进程非零退出，报告仍然先写出来。

### 延迟故障把正文按 gzip 解了两次

现象：种子 42、6 次请求的第一次联调，`cell_valid=false`，原因是 `trace=1 fired=5`。trace 里只有 `value_fault`。四次 `latency_spike` 没有 `fault_injected`。服务时间把注入的睡眠也算了进去。单独重放第二次请求时，错误是 `http_error:Error -3 while decompressing data: incorrect header check`。

原因：DeepSeek 的响应带 `content-encoding: gzip`。`FaultTransport` 先 `aread()`，这一步已经解开正文。再包一层新响应时，头里的 gzip 还在。httpx 客户端按这个头又解一次，明文 JSON 不是 gzip，于是失败。异常发生在读完响应之前，故障标记到不了 `usage`。`value_fault` 不经过上游响应，所以只有它被记下来。

处理：正文已经解开之后，去掉 `content-encoding` 和 `content-length`，再把故障放进响应扩展。测试用一段真正的 gzip 正文包住合法的工具调用，确认延迟故障仍是 `completed`，并且 `fault_kind` 是 `latency_spike`。修好后用同一个种子重跑，5 条故障都在 `results/v0.4/trace.jsonl` 里，样本已减去 `delay_s`。

### PowerShell 读不了结果里的中文 JSON

现象：用 `Get-Content | ConvertFrom-Json` 读 `service_prior.json` 报未终止的字符串。

原因：默认编码把文件末尾的中文说明截坏了，JSON 本身是 UTF-8，内容是完整的。

处理：第二轮冒烟直接传入已经量到的 p50 数字，不从 PowerShell 解析这个文件。

## v1.0

### 公平槽理由里的 `reserve` 被架构测试拦住

现象：`fair slot reserved` 让「运行时源码不得出现工具名」的测试失败。

原因：测试把子串 `reserve` 当成库存写工具。公平槽的理由里用了这个词。

处理：改成 `fair slot held`。占到份额的派发理由是 `fair slot; oldest executable`。

### 刷新间隔的睡眠让同一种子对不上

现象：同一策略、同一种子重放两次，`observations_refreshed` 和 `decision_wait` 的条数不一样。

原因：间隔用 `asyncio.sleep` 等墙钟。机器忙的时候，下一次决策看到的间隔已经过了。

处理：遇到 `refresh interval` 时把逻辑时钟跳过最小间隔，不再睡。绝对时间可以不同，事件类型、原因和任务 id 必须相同。

### J1 一直选择等待

现象：观测已经对齐时，J1 仍不派发。

原因：`wait` 的成本只有 `epsilon`，效用约 `1/epsilon`，比执行更高。

处理：`wait` 的效用固定为 0。刷新只在缺观测、版本差或前提为假时可用；已经对齐则刷新效用为 0。

### 预算是 1，trace 里同一任务却刷新了三次

现象：`refresh_budget=1` 时，`run_finished` 记下的预算是 1，但 `t0` 有 3 条 `observations_refreshed`。

原因：刷新池按 `merge_key` 合并在途观察，等待方不再增加 `used`。运行时仍为每个等待方写一条刷新事件。调度器读到的 `refreshes_used` 还是 0，于是继续发刷新。

处理：接受一次刷新决策时就给该任务记一次预算。超过上限只写 `decision_wait`，原因是 `refresh budget exhausted`。物理 `observe` 仍按 `merge_key` 合并。

### 版本冲突把运行打满步数

现象：多任务共用库存时，`exceeded max_steps`。trace 尾部反复是版本冲突、作废尝试、新开尝试。

原因：一次成功提交会推进库存版本，但 B0 忽略 dirty，下一笔仍提交旧观测。运行时把版本冲突当成可以重规划的理由，没有上限。

处理：同一任务的这类重开最多 3 次，然后记为拒绝。库存不足本来就会终态拒绝。静态外生增量为空时，J1 不再因为自己的提交去追加刷新。

## v1.1（阶段 A–D 与就绪审计）

### 只把 `resource_reclaim_observable` 改成 `False` 会把 `local_read_stopped` 一起弄丢

现象：阶段 B 修口径时，为了防止把客户端 `response.aclose()` 误报成服务端资源回收，把 `HttpStreamingBackend` 的 `resource_reclaim_observable` 改成了 `False`。结果 B 臂连本地读取停止事件 `local_read_stopped` 与 `cancel_latency_s` 都变成了空。

原因：`runtime.py` 原先让 `local_read_stopped` 和 `resource_reclaimed` 共用同一个条件 `if receipt.reclaimed and caps.resource_reclaim_observable`。

处理：将两个条件拆开。只要 `receipt.reclaimed` 为真（即本地流式读取循环确实因取消退出），就无条件发出 `local_read_stopped`；只有 `caps.resource_reclaim_observable` 也为真时才发 `resource_reclaimed`。客户端流式后端永远只发前者，不发后者。

### `eligibility_revoked_at` 与 `cancel_requested_at` 在阶段一里指同一条事件

现象：阶段一 60 行里，`eligibility_revoked_at` 和 `cancel_requested_at` 数值完全相等，算出来的检测延迟其实是「库存改变到发出取消请求」。

原因：`gateway.linearize_revoke` 在锁内把 `attempt.eligible` 置为 `False` 时没有单独向 `EventLog` 发事件，汇总代码只能退而求其次取 `cancel_requested` 的时间戳。

处理：在 `gateway.linearize_revoke` 成功将资格从真改假时，立即发出独立的 `eligibility_revoked` 事件；`detection_latency_s` 改为 `eligibility_revoked_at - stock_change_applied_at`。不回写阶段一原始 60 行，新口径从阶段 B/C 起生效。

### 流式增量 `tokens: 1` 与供应商计费词元混淆

现象：每收到一条 SSE 增量就记 `usage={"tokens": 1}`，既包含了 `tool_call_delta`，又容易被误读成供应商计费 token。此外，B 臂调用 `response.aclose()` 断流后，上游根本不会发最后一条带 `usage` 的 chunk。

原因：SSE 增量次数是客户端事件数，不是 tokenizer 词元，更不是服务端实际生成的 token。

处理：本地流式增量改记 `event_count: 1, usage_source="local"`；新增 `text_tokens.py` 冻结 `tiktoken` + `cl100k_base` 单独统计客户端收到的可见文本词元 `post_revocation_observed_text_tokens`；供应商 `provider_completion_tokens` 只在 `completed` 事件明确携带该 attempt 的供应商 usage 时记录，B 臂断流后一律记为 `"UNKNOWN"`。

### 阶段一归档 `code_version=6de2721` 与实际生成代码快照不一致

现象：阶段一 `matrix.jsonl` 每行都写着 `code_version="6de2721"`，但直接检出 `6de2721` 根本没有 `http_streaming.py` 和矩阵脚本。

原因：跑阶段一时工作树有未提交的新增流式代码，`git rev-parse --short HEAD` 读到的是当时的基线提交 `6de2721`，实际快照直到后续提交 `1c795c5` 才进版本库。

处理：在 `results/archive/phase1/manifest.json` 中诚实记录 `recorded_code_version_in_rows="6de2721"` 与 `actual_snapshot_commit="1c795c5"` 的历史差异，不篡改原始 60 行 JSONL，提供只读重算脚本 `scripts/recompute_phase1_summary.py` 验证汇总完全一致。

### 确定性可恢复任务若异步延迟加回库存，会被快速重规划直接判死

现象：写确定性 `ScriptedValidityBackend` 的可恢复用例时，如果在触发点用 `asyncio.sleep(0.05)` 延迟加回库存，假后端不睡网络 I/O，重规划的新 attempt 在 1 毫秒内就会完成观察并看到 `stock=0`，随后因 `insufficient stock` 把整个任务置为终态 `REJECTED`，等不到 50 毫秒后的恢复。

原因：`runtime._handle_rejection` 只对版本冲突、租约过期、资格失效做重规划，遇到 `insufficient stock` 会直接 `complete_task(REJECTED)`。

处理：分两步解决。阶段 C 的状态谓词确定性测试在同一触发回调内同步执行清零与加回（验证状态转移谓词）；到了阶段 E/F 的独立定时 `ScenarioDriver`，在 `Runtime` 中新增 `await_recovery_on_depletion`，当可恢复任务在恢复窗口前因 `insufficient stock` 被拒时进入 `_awaiting_recovery` 等待池，待后续外生恢复事件到达（`source_dirty`）时自动唤醒并开启新 attempt。

## v1.2（阶段 E 主实验与阶段 F 边界/队列/合同）

### 重规划轮次的后端失败把首轮已成功触发的 `triggered` 覆盖成了失败

现象：E1 开发种子跑完后，`mid_early`（`seed=1041`）和 `long_late`（`seed=1091`）的首轮请求明明在 `0.25s / 1.80s` 正常触发了资格撤销（`eligibility_revoked_at` 非空），行里的 `trigger_outcome` 却被标成了 `model_no_action` 或 `transport_failed`。

原因：`_classify_trigger_outcome` 扫描了整次运行全部 attempt 的 `backend_failed` 事件。当首轮 attempt 被撤销后，Runtime 自动发起的重规划 attempt 如果偶发遇到模型没调工具或网络断连，就会把首轮原本已经成功触发的 `triggered` 状态覆盖掉。

处理：将首轮取消触发状态与重规划阶段失败拆开。`_classify_trigger_outcome` 只检查发生在 `eligibility_revoked_at` 之前（或首轮 attempt 自身）的失败；重规划阶段的失败单独记入 `replan_backend_failures` 与可用性统计表，不抹杀首轮已触发的事实。

### 外生变化触发前已自然完成的短任务被误算成 `old_attempt_committed=True`

现象：E2 低收益边界格（`short_late`，50 词，`t_change=1.80s`）中，模型在 1.80 秒外生变化发生之前就已经把 50 词和 `reserve` 工具调用全部生成完并合法提交了。但初版提取逻辑只要看到 `task_kind in {"invalidate", "recoverable"}` 且首 attempt 提交，就标 `old_attempt_committed=True`。

原因：混淆了「请求在外生变化前已自然完成（`trigger_not_fired`）」与「资格已被撤销的旧 attempt 越权提交」。

处理：严格修正定义：`old_attempt_committed` 仅当 `eligibility_revoked_at is not None`（即该 attempt 确实被撤销了资格）且该首 attempt 仍然发生了 `action_committed` 时才为 `True`。同时在阶段 F 中增加 `successful_cancellation` 与 `successful_recovery` 字段，强制要求只有 `trigger_outcome == "triggered"` 时才可为真，绝不把未触发的自然完成算成取消成功或恢复成功。

### 多任务 FIFO 队列下，排在后面的任务提交推进了库存版本，导致队尾重规划任务连续 3 次版本冲突失败

现象：`test_f4_fifo_scheduler_replan_goes_to_tail` 离线测试中，`t0` 首轮被取消后重规划 `att-0007` 排到 `t1` 后面（进入队尾），并提前完成了重观察（读到恢复后的版本 `v3`）。接着 `t1` 获得槽位并成功提交，使环境库存版本从 `v3` 推进到了 `v4`（但这一步是内部提交，不会产生外生 `changes` 事件把 `_dirty` 标脏）。随后轮到队尾的 `t0 (att-0007)` 派发并提交时，它绑定的还是 `v3`，被网关以 `version conflict` 拒绝；开启下一次重规划 `att-0018` 时，由于 `_dirty` 为空，调度器认为已有观测且未脏，不触发重观察，继续拿旧观测 `v3` 提交，连续撞满 3 次重规划上限后任务被判 `REJECTED`。

原因：多任务共享同一库存源时，同批其他任务的合法提交会推进环境版本，但不会像外生变化那样通过 `_poll_changes` 把来源标进 `self._dirty`。

处理：在 `Runtime._handle_rejection` 中，当可恢复模式（`await_recovery_on_depletion=True`）因 `"version conflict"` 触发重规划时，将该任务当前绑定观测对应的 `source_id` 显式加入 `self._dirty`，强制新 attempt 在派发前重新观察最新版本号。同时保留单任务静态负例矩阵的原行为（不破坏 `test_static_joint_observes_once_per_task` 等 119 项既有测试）。

### Git 提交与推送 GitHub 时的身份与代理问题

现象：在阶段 F 工程冻结执行 `git commit` 时报 `Author identity unknown`；随后 `git push origin main` 报 `Recv failure: Connection was reset`。

原因：当前机器未配置全局 `user.name`/`user.email`，且 Git 默认直连 GitHub 未走本机 `127.0.0.1:7890` 代理端口。

处理：使用仓库历史提交者身份并通过 `git -c http.proxy="http://127.0.0.1:7890" -c https.proxy="http://127.0.0.1:7890" push origin main` 完成推送。

## v1.3–v2.0 口径补记

这些不是 3.0.0 新跑出来的数字，是当时已经写在测试记录里、但没有收进本问题记录的口径。

### 客户端停读不是供应商取消

现象：B 臂和 C 臂调用 `response.aclose()` 之后，本地不再读流，槽位也释放了。

原因：断的是客户端读。代码没有调用供应商的取消接口，`provider_abort_not_issued` 保持为真。服务端是否还在算、是否还在计费，没有观测。

处理：文档和 README 把这句写成限制。不把本地槽位差写成 GPU 或 KV 回收。

### 普通断流就能解释有害路径上的停读速度

现象：v2.0 有害确认性里，三臂都触发的 74 对上，B 与 C 的槽位差是 0.005 秒，文本差约 0.2 词元。

原因：两边都停了本地读。前提判断没有再加快断流。

处理：不把 B−C 的速度差写成前提感知的收益。前提感知的增量放在无害路径：B 误撤 146/180，C 是 0/180。

### v1.8 的后续等待不是旁观者 P95

现象：FIFO 上 A−C 的后续任务首次等待达到预先写下的 1 秒（中负载均值 4.107 秒，区间 [2.993, 5.163]）。SJF 没有达到。

原因：`batches.jsonl` 的 980 行有 `first_queue_wait_s`，没有 `workflow_role`，也没有 `slot_reacquired_by`。后续任务里混着队里的其他人，分不出旁观者和后继。

处理：2026-11-03 的只读审计把结论写成“不能改名”。主证据改由 v2.1 回放重新产生。

## 3.0.0 回放

### 有害路径上，刚放出的槽先被 successor 接走

现象：确认性有害 G2 的 `slot_reacquired_by` 全部是 successor，共 600 条。旁观者 P95 等待相对 G0 仍然下降，12 个主格都跨过 10%。

原因：G0 会把失效尾巴继续占满，然后再跑同样长度的 successor。G2 少占的是这段尾巴。下一手是 successor，不等于旁观者没有少等。

处理：机制报告同时写接收者和等待差。不把“槽被后继接走”写成旁观者没有收益，也不把收益写成槽直接交给了旁观者。

### 无害路径上，rho 会把选择性的方向反过来

现象：\(\rho_b=0.5\) 时，G2 的旁观者 P95 比 G1 更差。\(\rho_b=1\) 时差为 0。\(\rho_b=2\) 时 G2 更好，并跨过 10%。

原因：G1 会误撤并立刻放入 restart。restart 比剩余有效服务短时，误撤反而少占槽。G2 把有效尾巴读完，旁观者等得更久。

处理：主表保留负的格子。结论不写“选择性总是减少排队”。

### 无害格子上 Runtime-PLAS 和 FCFS 的旁观者数字相同

现象：无害三档 rho 上，两种调度的 ΔW95 逐位一样。有害格子上两者不同。

原因：这条工作负载只有一个焦点工作流积累了已完成服务。旁观者的已完成服务是 0，restart 因为同一 `workflow_id` 排到后面，效果和 FCFS 的队尾重规划一样。

处理：论文里把它们标成同一工作负载上的重合，不把两列写成两次独立复现。SRPT 在无害 \(\rho_b=0.5\) 和 \(\rho_b=2\) 上与 FCFS 方向相同、幅度不同。

### 完成率没有拉开

现象：确认性每条旁观者都在排水窗口内完成，完成率差是 0，没有碰到 2 个百分点的伤害线。

原因：窗口是最后一次到达再加 64 秒，4 个槽下队列没有把旁观者留到窗口外。

处理：完成率表照实写成 1.0。这轮的旁观者效应写在等待和完成时间上，不写完成率优劣。

### 延迟释放和继续占槽是同一条队列时间线

现象：边界格 G2-delayed-release 的旁观者 P95 均值与同格 G0 相同，都是 14.233 秒。

原因：延迟释放一直占到原服务结束，再放 successor。旁观者看到的占槽和 G0 一样。少等需要事件发生时就放槽。

处理：边界报告写明这一点。不把延迟释放的空差写成测量失败。
