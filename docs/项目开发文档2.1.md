## 2. 阶段一：已经看到的，以及推不出的

模型 `deepseek-chat`。正式矩阵 30 对、60 次流。A 臂撤销资格后继续读。B 臂撤销资格并 `response.aclose()`。每格计划 5 对。数字由 `summarize_cell` 从原始行重算，与 `matrix_summary.json` 一致。分支是 `uncertain`。这是探索，不是主实验，没有置信区间。

`post_revoke_local_deltas` 把 `token_delta` 和 `tool_call_delta` 加在一起。它是客户端看到的增量事件条数。原始行没有分开两类事件，也没有 tokenizer 词元，也没有能归因到单次请求的供应商 `completion_tokens`。下文把这个字段叫撤销后增量事件数。

30 个 B 臂的撤销后增量事件数都是 0，所以六格中位数都是 0。A 臂中位数大于 0。六格有效提交都是 0：库存被改成 0 之后，预约不能提交。这不能用来说明取消提高了有效吞吐。

| 格 | 计划 / 触发 / 有效 / 失败 / 未触发 | 当次事件节省中位数 | 系统事件节省中位数 | 撤销后事件差中位数 | A 撤销后事件中位数 |
| --- | --- | --- | --- | --- | --- |
| 300 词，0.1 秒 | 5 / 5 / 5 / 0 / 0 | 0.950 | 0.230 | 465 | 465 |
| 300 词，0.5 秒 | 5 / 5 / 5 / 0 / 0 | 0.762 | 0.236 | 428 | 428 |
| 300 词，1.5 秒 | 5 / 5 / 4 / 0 / 0 | 0.376 | 0.110 | 274.5 | 274.5 |
| 50 词，0.5 秒 | 5 / 4 / 3 / 0 / 1 | 0.178 | 0.044 | 31 | 31 |
| 800 词，0.5 秒 | 5 / 5 / 5 / 0 / 0 | 0.851 | 0.224 | 837 | 837 |
| 3 任务，300 词，0.5 秒 | 5 / 5 / 3 / 2 / 0 | 0.705 | 0.059 | 373 | 373 |

当次节省的分母是两臂被撤销那一次的全部增量事件，不含重规划。系统节省的分母含两臂后续事件和记在 `replan_local_deltas` 里的事件。1.5 秒格有效对是 4，中位数是中间两数的平均。差值为负的有效对是 0。

B 臂本地读停止减 `cancel_requested` 的中位数约 0.005 到 0.010 秒。库存实际改变到 `cancel_requested` 的中位数约 0.004 到 0.025 秒。行里的 `eligibility_revoked_at` 和 `cancel_requested_at` 取的是同一条 `cancel_requested` 事件。代码里 `linearize_revoke` 发生在发出这条事件之前，但轨迹没有单独的资格撤销时刻。阶段一协议写的检测延迟，在这批行里其实是「库存改变到取消请求事件」。

长文本上，A 继续读旧请求，端到端长于 B。0.5 秒格和 50 词格里，B 的 `replan_local_deltas` 中位数高于 A。三任务格里，这个字段还包含另外两个任务的增量，不能当成目标任务自己的重规划。

没有放进节省率、但必须留在表里的行：

- 种子 113 的 A、种子 202 的 A：`unexpected_tool_call`。
- 种子 203 的 A：库存回调发生了，没有 `cancel_requested`，`trigger_not_fired`。50 词触发率 0.8。
- 种子 402 的 B：两条 `http_error:`，异常文本是空的。种子 403 的 B 有 `http_error:`，A 是 `stream_closed`。这两对记失败。

若干 `completed` 行的 `backend_failures` 含 `backend returned no action`。那是后续尝试没有工具调用。传输没有失败，所以没有从节省率里拿掉。

预检三次都提交成功，库存 3 到 2，端到端 1.81 / 3.52 / 6.80 秒，没有顶到 120 秒。800 词预检在工具调用前是 640 个空白分词，短于目标。静态预约 6 次都是 `reserve`、`qty=1`、库存 3 到 2。那是另一批任务，外生变化为空，不能和本矩阵的 0 提交混成一个结论。

中断文件 `matrix_aborted.jsonl` 和 `matrix_aborted_422.jsonl` 保留。第二次中断的原因已经能对上代码：读工具把观测列表放进 `content`，DeepSeek 返回 422，缺 `type`；流结束但没有工具调用时，异常分支当时没有导入 `json`。正式行是这两处改过之后写的。

### 2.1 这批数据不能支持的句子

- 不能写已经测出词元浪费，或节省了多少 token。事件条数不是词元。
- 不能写 GPU、KV cache、推理循环或供应商账单已经下降。`aclose` 停下的是这一次 httpx 响应的本地读。
- 不能写有效吞吐提高。六格有效提交都是 0，因为实验把库存设成 0。
- 不能把 20% 和 5% 说成显著性阈值。它们是阶段一协议里的项目门槛。50 词当次节省 0.178 落在中间，整份矩阵因此标成不确定。
- 不能把 108 项离线测试写成生产就绪，也不能把单机原型写成分布式运行时。
- 不能把 `resource_reclaimed` 事件当成服务端回收。见第 3 节。

## 3. 取消在代码里实际做了什么

`_do_cancel` 先 `linearize_revoke`，再 `_emit_cancel`。资格和连接是两次操作。

| 层级 | 现在有没有证据 | 代码里的对应 |
| --- | --- | --- |
| `cancel_requested` | 有。轨迹事件 | `_emit_cancel` 开头 |
| `eligibility_revoked` | 资格会改。阶段一行没有独立时间戳 | `linearize_revoke` 在锁内 `supersede_attempt`。已持有提交权或已 `COMMITTED` 则撤销失败 |
| `connection_closed` | B 臂调用了 `response.aclose()`。没有单独事件 | `stop_on_cancel` 为真才关闭。A 臂回执文本是 `cancel_accepted_compute_may_continue` |
| `local_read_loop_stopped` | B 臂有 `local_read_stopped` | 读循环看到取消标志后返回，或在 `aclose` 引起的读错误里返回。`reclaimed` 只表示这件事 |
| `provider_cancel_accepted` | 无 | 没有调用供应商取消端点 |
| `provider_generation_stopped` | 无。标未知 | 关闭响应不能升级成这一层 |
| `server_resource_reclaimed` | 无。标未知 | 见下一行 |

`HttpStreamingBackend.capabilities()` 把 `resource_reclaim_observable` 设为真。读循环停下且回执 `reclaimed` 时，运行时同时发出 `resource_reclaimed` 和 `local_read_stopped`，原因都是「本地循环已停」。模型里的 `BackendCapabilities` 写明取消确认不等于计算已经停止。这里能力位和事件名越过了证据。非流式 `HttpToolBackend` 的同一标志是假。阶段一原始行没有保存这条 `resource_reclaimed` 事件，汇总也没有用它。

每个流式增量事件的 `usage` 是 `{"tokens": 1, "usage_source": "local"}`。这里的 `tokens: 1` 是一条事件计 1，不是 tokenizer 的词元。供应商 usage 只在 SSE 带了 `usage` 对象时，附在该次 `completed` 上，并标 `usage_source=backend`。B 臂在工具调用前关掉读，通常等不到这条 usage。随后的重规划如果完成，会再带上另一次请求的 usage。`真实api.md` 里的 `provider_usage` 是整条轨迹最后一次 usage，混有重规划。不能归因的请求必须记 `UNKNOWN`，不能用别的请求代替。

迟到结果：成功确认的流式取消不会把 attempt 放进 `_block_late`。B 臂靠读循环不再交出 `completed`。已经拼完并交给网关的结果，仍会走到 `submit`，再因资格失败被拒绝。A 臂故意不关连接，完整工具调用会到达网关。取消失败、不支持取消、没有句柄时，才把该尝试放进 `_block_late`，迟到结果不再提交。旧结果是否进网关，取决于它在关闭前有没有被交出去，不是关闭本身的自动推论。

半截工具参数留在 `argument_text`。读循环关闭后的包不再追加，也不会补成 `CandidateAction`。这有离线测试，没有写进阶段一的原始行。

重规划：取消后若截止还在且没有未关闭尝试，会 `begin_attempt`。拒绝原因属于过期、版本冲突或资格失败时，同一任务最多再规划 3 次。库存不足的拒绝不在这组原因里，任务可以就此 `REJECTED`。没有工具调用且尝试仍有资格时，任务记 `backend_failed`，原因是 `backend returned no action`。阶段一把传输失败标成 `model_error`，把「没有工具调用」留在 `completed`。

并发失败还不能归到一个原因。三任务格 `max_inflight=1`，一个运行时里流式请求是串行的。每次请求自己建 `httpx.AsyncClient`，不是进程内连接池打满。归档原因只有空的 `http_error:` 和 `stream_closed`（取消标志未置位时的读错误或协议错误）。异常类型、HTTP 状态码和响应体都没留下。限流、超时、服务端提前断开都还可能。这 2 对不能删。

锁：提交权在锁内取得，`environment.commit` 也在这把锁里调用。外部提交成功后本地确认失败会发 `commit_unknown`，不记成已提交。`check` 仍在锁外，检查和写入之间的窗口还在。这不是跨系统原子提交。这把锁在未提交工作树里，不在 `6de2721`。

## 4. 要回答的问题

一次推理正在进行，它依赖的外部状态变了，这次 attempt 失去资格。运行时是继续让旧请求生成、等结果回来再拒绝，还是立刻撤销资格并停止本地读取？这种提前停止，在什么长度、时机和负载下，能测到对客户端可见输出和有效任务结果的差别？

### RQ1 客户端能观察到什么

- 状态变化之后，旧 attempt 还会向客户端送出多少文本增量事件、多少工具调用增量事件、多少可观察文本词元？
- 立刻停止读取，和只在网关拒绝迟到结果，两者的差别是否随长度、时机和负载变化？
- 这些差别能否与重规划、再次观察和排队分开？

阶段一支持的只有第一问的一部分：在这 30 对里，B 的撤销后增量事件数是 0，长文本上 A 的中位数是几百条事件。词元数、供应商账单和服务端停止都还没有。

### RQ2 有效任务有没有完成

只看旧 attempt 少输出，回答不了任务是否做成。需要三类任务：

| 类型 | 应当发生的事 | 现在的证据 |
| --- | --- | --- |
| 静态有效 | 状态不变，读到库存并提交一次正确数量 | 静态预约 6/6，库存 3→2。预检三次同样提交成功。都不是阶段一矩阵 |
| 失效 | 状态变化后，旧 attempt 不提交 | 阶段一有效提交为 0。库存被设成 0，两臂都无法提交。旧结果被拒绝这件事，A 臂更直接；B 臂多半是结果没再送到网关 |
| 可恢复 | 旧 attempt 失效后，重新观察和规划，在新条件下成功提交恰好一次 | 没有这种正式行。阶段一的重规划发生在库存已经是 0 的时候 |

只有可恢复任务里新计划提交成功，才能讨论取消对有效完成的影响。副作用必须只发生一次。

### RQ3 什么时候不值得做

静态、低负载、短任务、观察很贵、后端不能取消、突发、多任务排队、可能饿死长任务的负载、并发传输不稳定。阶段一已经碰到其中三个迹象：50 词系统级事件节省中位数 0.044；短回复可以在回调前结束；三任务有 2/5 对传输失败。这些是负例的起点，不是完整的负例矩阵。假后端上已有的负例断言只说明机制会退回，不报告差值。

## 5. 假设，以及什么结果会收窄它

| 假设 | 会被什么收窄 |
| --- | --- |
| H1 长生成上，停止本地读取会减少客户端在撤销后看到的增量事件和可观察文本词元 | 固定 tokenizer 之后，长任务的词元差中位数接近 0，或只在事件条数上出现、文本词元上消失 |
| H2 这种减少能和重规划、观察、排队分开，并且在可恢复任务里不降低一次成功提交 | 可恢复任务中，B 的完成率或端到端差于 A，差额大于词元差所代表的等待；或重规划事件数吞掉当次差 |
| H3 短任务、静态任务和低负载上，提前停止没有可测收益 | 这些格子上当次差和系统差都很大。那样就不是「只在长任务上值得」 |
| H4 联合打分比临近准入多解释了一部分有效完成 | 关掉打分或关掉公平槽都不改变决策，或两者的有效完成区间重叠。阶段一没有检验 H4 |

H1 在事件条数上有探索性支持，在词元上未测。H2、H3、H4 都还没有正式证据。版本变化率不是真实失效率。服务时间先验为 0 表示还不知道要多久，不表示总能按时完成。

## 6. 指标

下一轮原始轨迹要能指出每个数的分子、分母、单位和未知来自哪一次请求。阶段一协议先不改。下面是建议的新口径，正式开跑前另写协议。

| 字段 | 含义 | 阶段一有没有 |
| --- | --- | --- |
| `post_revocation_delta_events` | 资格撤销之后客户端看到的文本增量事件条数 | 没有单独字段。它和工具增量混在 `post_revoke_local_deltas` |
| `post_revocation_tool_call_delta_events` | 同期的工具调用增量事件条数 | 没有 |
| `post_revocation_observed_text_tokens` | 用冻结名称和版本的 tokenizer，对客户端实际收到的文本重算。只说明客户端收到多少文本 | 没有。`actual_words_before_tool` 是空白分词 |
| `provider_completion_tokens` | 供应商对该 attempt 的 completion usage。不能归因则 `UNKNOWN` | 矩阵行没有。180 词记录是整条轨迹最后一次 usage |
| `server_compute_saved` 及 GPU、KV、账单 | 有服务端或账单证据才可写已知值 | 没有。保持未知 |

还要分开记：请求开始、首个增量、资格撤销、连接关闭、本地读停止、尝试终态。检测延迟是资格撤销减状态实际改变。取消延迟是本地读停止减取消请求。两个都不能合成一个「取消延迟」。

统计单位仍是一对或一格，先按对算再取中位数、最小值、最大值。未触发和失败留在表里，节省率是 null，不填 0。差值为负则保留。开发种子和测试种子分开。看过测试种子之后不再改参数。

## 8. 联合打分先不进入正式对照

`JointScheduler` 已在 v1.0 代码和假后端协议里。阶段一没有跑它。真实 API 上还没有可恢复任务的完成差，也没有稳定到可以解释的系统级事件差：50 词系统节省中位数 0.044，三任务是 0.059 且 2 对传输失败。

进入正式对照的条件，三条都要有：

1. 阶段 E 里，提前停止相对「只拒绝旧结果」有稳定的客户端可观察差别，并且可恢复任务的一次提交没有变差。
2. 临近准入解释不了剩余的有效完成差。
3. 关掉打分、关掉公平槽，各自都会改变决策理由。公平槽和打分必须能单独关。先验为 0 保持「未知」，不写成总能完成。

三条里缺一条，就不做联合打分研究。不为了留下算法而加实验。不把调参后的开发种子写成全局最优。

## 9. 工程路线

论文数据阻塞项按 A→B→C→D→E→F。工程项可以并行，不能代替原始行。

| 编号 | 工作 | 验收时能看到什么 | 和论文的关系 |
| --- | --- | --- | --- |
| 工1 | 流式取消的证据分层 | 本地读停止有事件。能力位不再把这件事标成资源回收。供应商取消端点若存在，回执单独记 `provider_cancel_accepted` | 阻塞阶段 B |
| 工2 | 资格与提交的锁保持可复核 | 锁内写明何时取得提交权、何时外部副作用已发生、外部成功但本地确认失败时为 `UNKNOWN`。`check` 在锁外这件事写在能力说明里 | 阶段 C 的「恰好一次」依赖它。它本身不是新实验 |
| 工3 | 有界准入队列和有界刷新池 | 满则拒绝或等待，进程不因队列耗尽内存退出。运行开始和结束、提交、拒绝、取消、本地读停止、任务终态不丢 | 过载负例一起做。不阻塞阶段 C |
| 工4 | 事件缓冲背压 | 可丢弃的重复等待要计数。关键事件不丢 | 同工3 |
| 工5 | 多进程会话租约和跨进程序号 | 同一会话并发准入恰好一个成功。序号由库自增 | 不阻塞论文数据 |
| 工6 | 重启恢复 | 未终态在重启后可读。不把崩溃恢复性能放进主矩阵 | 不阻塞 |
| 工7 | 调用链导出 | 离线文件能解析根跨度和子跨度。复现仍以事件轨迹为准。CI 不启动外部界面 | 不阻塞 |
| 工8 | 配置版本、探活、优雅退出 | 不认识的配置版本拒绝启动。终止信号后不登记新任务 | 不阻塞 |

2.0 的 5.1 验收要求轨迹里出现「资源已回收」。按现在的证据，那一步改成「本地读循环停止」。服务端释放键值缓存继续不作为验收。5.2 的「可以丢弃重复等待」必须带计数，关键事件列表保持不丢。5.3 的「恰好一个准入成功」仍然可测。5.4 的探活和退出仍然可测。

工1 要改的是能力位和事件名，以及缺了就写 `UNKNOWN` 的 usage。不把「未来可以接 vLLM」写成已经能观察 GPU。

## 10. 论文方向等数据打开

| 数据 | 方向 | 还不能写的标题句 |
| --- | --- | --- |
| 可观察输出减少稳定，可恢复任务的一次提交不受损，联合打分没有独立优势 | 论文写取消机制的适用条件 | 不写联合调度提高了吞吐 |

只证明客户端关掉响应后不再收到字节，和 HTTP 客户端的既有行为太近，还不够当成贡献。贡献要落在：失效资格、迟到结果拒绝、重规划成本，以及这些差别在什么长度和负载下还在。相关工作没核完之前，不写「取消是新方向」。

要读完并分开写的相邻工作：

- *When Agent Context Goes Stale: Incoherence in Volatile Agent Context*。现有参考目录里的 Concord。它讨论易变上下文的不一致。EpochGate 没有复现它，阶段一也不是它的验证。
- *Stale Does Not Mean Unsafe: Guard Precision for Tool-Using LLM Agents under Infrastructure State Races*。现有参考目录没有这一篇。它和上一篇不是同一篇。没有读完之前，不写 EpochGate 与它的差别，也不写它支持了本项目的结论。

还要核对的范围：LLM serving 里的取消、抢占和请求调度；流式 HTTP 的中止和断连；Agent 执行中的放弃和重新规划；过时结果拒绝和外部副作用隔离；依赖感知刷新。核对之后只保留和本问题重叠的句子，并写明 EpochGate 还缺哪一类证据。

## 12. 不做，以及对外怎么说

不做：训练模型、多 GPU 内核、集群控制器、租户计费、机器人低层、官方榜单、为了题目再加一个学习型调度器、把第二环境接进来凑名次。

对外可以讲的：单机运行时里，资格、提交和本地流式读取是分开的；在 deepseek-chat 的 30 对探索里，关闭响应之后客户端不再收到该次请求的增量事件，继续读的一臂还会收到；短任务和并发传输没有给出同样干净的系统级差别；有效提交实验当时是 0，因为库存被设成 0。

对外不讲的：词元已经省下、GPU 或 KV 已释放、账单已下降、吞吐已提高、联合打分已优于临近准入、108 项测试等于可以承载真实流量。
