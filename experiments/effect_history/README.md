# 提交历史配对实验

按[事前协议](PROTOCOL.md)，现象在两个受测执行边界成立，新增配对调度的检出增量未建立。[冻结判决与逐格结果](../../results/experiments/effect-history/pilot-01/report.json)

27 个固定实验格的终态全部匹配，45 次落地效果的字节或摘要与持久回执相符。只看终态检出 0 格，加入授权、去重与回执仍检出 0 格。检查提交时的业务状态检出 4 格。它们均出现在预检通过、业务值随后改变、旧动作最后提交的窗口，合法后继随后把产物改成预期值。库存沿用已有实验问题，路由使用新设的确定性夹具。

| 执行配置 | 普通顺序 | 配对顺序 | 已有间隙强对照 |
| --- | ---: | ---: | ---: |
| SQLite 无围栏 | 0 | 2 | 2 |
| 文件发布 | 0 | 2 | 2 |
| SQLite 版本围栏 | 0 | 0 | 0 |

每列每个配置预算为 6 格。数值是检出的业务输入数。三个对照从同一矩阵取子集，存在共享格。强对照使用仓库已有的预检后、提交前状态更新能力。

旧动作先于业务变化而提交时，历史评分判为合法。对确实改变业务值的两个输入，SQLite 围栏拒绝间隙中的旧动作，保留合法后继。在仅推进版本的输入中，围栏也拒绝旧动作一次，该格终态仍完成。这条观察可用于研究安全与进展的权衡。

## 投稿判断

四格漏检可作为探索性证据。配对调度与已有强对照打平，本轮结果不足以把调度方法写成论文主贡献。下一关可选择一个真实历史案例或留出的任务，事前写明业务提交约束和后继义务，检验已有提交时业务断言漏掉什么，或测出可复核的安全与合法进展权衡。

历史确认批的 6/16 是成功子集上的过期凭证接纳。它属于授权问题，和这里的提交时业务违规分开报告。[历史审计](../historical_audit/audit_report.md)

## 复现

在 `experiments/` 运行。审计先检查归档 SHA-256，再从逐格账本、文件快照与时序记录重算报告。重跑使用新的输出路径。

```powershell
../.venv/Scripts/python.exe -m effect_history.run audit ../results/experiments/effect-history/pilot-01
../.venv/Scripts/python.exe -m effect_history.run run ../.epochgate/effect-history-new
```

SQLite 接收端使用原有事务函数进程内执行，文件使用现行 RunLedger 发布函数。两者共享实验控制器。文件分支的业务状态由控制器掌握，提交后立即读取目标文件，并核查持久发布事件与回执。实验使用确定性动作和顺序，没有模型重规划、操作系统崩溃、网络故障或并发写者。
